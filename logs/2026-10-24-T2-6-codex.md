# T2-6 Codex 검수 로그 (2026-10-24)

## 모드 C (설계 검수, 구현 전) — 3회
T2-6은 DB 스키마를 바꾸고(부분 유니크 인덱스) 새 공개 API(`PUT /songs/{id}/drumscore`)를 추가하는 "위험 작업"이라 `06-pipeline.md` §1-1에 따라 구현 전 설계 검수를 받았다.

**1회차: 수정 후 진행.** 필수 수정 2건:
- C-001: "조회 후 없으면 삽입"만으로는 동시 저장 요청 간 중복 `DRUMSCORE_EDITED` Asset 행 생성을 못 막음 — DB 레벨 부분 유니크 인덱스 + `IntegrityError` 시 명시적 복구 절차 필요.
- C-002: 파일 쓰기가 원자적이지 않아 서버 크래시 시 손상된 파일이 남을 위험 — 임시파일+`Path.replace()` 필요.
권장 C-003~C-009(실행취소 캡, 키보드 접근성 범위, BPM 범위 일관성, 부분 인덱스 범위 명확화, 응답 계약, last-write-wins 위험, EDITOR_ROWS/DrumPiece 커버리지)도 전부 반영.

**2회차: 수정 후 진행.** C-001 수정에서 `IntegrityError` 이후 `db.rollback()`을 재조회 전에 호출하는 절차가 빠짐, C-002의 "같은 볼륨"이 "같은 디렉터리"보다 느슨해 재현 안 되는 경우가 있음을 지적 — 둘 다 보강.

**3회차: 진행 가능.** 고정 임시파일명(`<파일명>.tmp`)이 동시 저장 요청 간 충돌 가능(새 C-001) — `uuid4` 기반 요청별 고유 임시파일명으로 수정, 구현 시작.

원문: `qa-evidence/T2-6/codex-modeC.md`, `-2.md`, `-3.md`

## 모드 A (독립 코드 검수)
판정: 필수 수정 1건(P1)
- **P1**: `grid.ts`의 `ticksPerGridUnit`이 ppq를 격자 분할 수(8분음표 셋잇단=3)로 나누는데, ppq가 3으로 나누어떨어지지 않으면(예: ppq=100) 결과가 정수가 아니게 되고, `score/validate.ts`의 정수 틱 검증을 통과 못 할 수 있음. 직접 계산으로 재현 확인(`snapTick(50, '8nt', 100) = 66.666…`). 코드 검토 중 방향키 이동(`moveSelected`)이 `snapTick`조차 거치지 않아 같은 문제가 하나 더 있었음을 추가 발견. `snapTick` 최종 결과 반올림 + `moveSelected`가 `snapTick`을 거치도록 수정, 회귀 테스트 2개 추가.

원문: `qa-evidence/T2-6/codex-modeA.md`

## 모드 B (보고서 대조) — 3회(최대)
**1회차: needs-attention.** 수동 브라우저 QA·PUT 요청 횟수 주장을 당시 `raw_log.txt`(자동 명령 출력만)로 교차검증 불가(medium), vitest 신규 테스트 파일별 개수 분해가 로그로 확인 불가(low).
→ 서버 접근 로그에서 PUT/GET만 추출해 `server-log-excerpt.txt` 커밋, `--reporter=verbose` 출력을 raw_log.txt에 추가.

**2회차: needs-attention.** 1차 발췌본은 PUT이 "있었다"는 것만 보여줄 뿐 "그 외엔 없었다"를 증명 못 함(medium).
→ 필터링 없는 전체 서버 접근 로그로 교체.

**3회차(최대 횟수): needs-attention.** 로그에 종료 표식이 없어 "전체 세션을 다 담았다"는 보장이 작성자 설명에 의존(medium), 저장→재오픈 동일성·PracticeCanvas 반영 같은 수동 관찰 주장은 접근 로그(상태코드만 기록)로는 원천적으로 검증 불가(medium).
→ 서버 프로세스를 실제로 종료해 로그 경계 확정, REQ-03 핵심 주장의 1차 증거를 `test_save_then_reload_matches`(바이트 단위 pytest assert)로 재배치해 문서에 명시, QA 원복 후 실제 GET 응답 본문을 커밋해 테스트 노트 미존재를 직접 증명, PracticeCanvas 주장을 "코드 경로 공유 확인"으로 범위 축소.

`06-pipeline.md` §1-1의 "재검수 최대 3회" 규칙에 따라 모드B는 3회에서 종료 — 이후는 Codex 재호출 없이 마스터가 직접 보강하고 진행.

## 결론
모드B 3차 이후 종료 → 마스터가 직접 로그 경계를 닫고(서버 프로세스 실제 종료) 증거 성격을 구분해 문서화한 뒤 `main` 병합 진행. 이번 작업의 핵심 교훈: (1) DB 스키마+공개 API를 같이 바꾸는 작업에서 모드C 설계 검수가 동시성·원자성 버그 3종을 코드 작성 전에 잡아준 것은 T2-5에 이어 두 번째로 확인된 패턴 — "위험 작업 전 설계 검수"가 이 프로젝트에서 반복적으로 비용 대비 효과가 있음이 쌓이고 있다. (2) jsdom 기반 자동 테스트로 잡을 수 없는 버그(가로 스크롤 시 레이블 소실)는 여전히 실제 브라우저 수동 QA에서만 발견됐다 — DOM 기반 UI라 RTL 테스트 커버리지가 T2-3~T2-5보다 훨씬 넓어졌지만, 레이아웃/스크롤처럼 jsdom이 계산하지 않는 영역은 수동 QA를 대체하지 못한다. (3) QA 문서에서 "자동화 테스트가 이미 증명하는 주장"과 "수동 관찰로만 뒷받침되는 주장"을 섞어 쓰면 후자에 대한 의심이 전자까지 끌어내린다 — 핵심 수용 기준은 애초에 어느 증거가 1차인지 문서에 먼저, 명확히 썼어야 한다.
