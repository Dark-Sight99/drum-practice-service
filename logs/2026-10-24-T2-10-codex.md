## 모드 B (보고서 대조) — 3회(최대)
**1회차: needs-attention.** 수동 QA(스크롤 중 항상 보임, R/L 가독성, 필인 로직 확인)와 "누락이었다" 확정 주장이 `raw_log.txt`·`codex-modeA.md`로 뒷받침 안 됨(medium) — 자동 검사 결과와 재현 불가능한 수동 서술이 구분 안 됨.
→ `grep` 명령 전문+종료 코드를 `raw_log.txt`에 추가, "항상 보임" 근거를 코드 구조(매 프레임 조건 없이 실행)로 재배치하고 스크린샷은 "그 구조대로 실제 렌더링된 한 시점 샘플"로 격하, sticking 로직 확인 범위를 "이번 관찰은 설계와 모순되지 않음"으로 축소.

**2회차: needs-attention.** `lane.label`/`LANES[...].label` 패턴만 검색한 grep의 exit 1이 "머리글 그리기 코드 전체 부재"를 확정하진 않음(medium) — 다른 변수명·방식으로 그렸을 가능성을 배제 못 함, 수정 전후 검색 패턴도 일치하지 않음.
→ 특정 식별자 패턴 대신 Canvas에서 텍스트를 그리는 `fillText` 호출 전부를 센 전수 검사로 교체 — main 283줄 전체에서 `fillText`가 정확히 1건(기존 스티킹 글자)뿐임을 확인, 변수명과 무관한 근거로 보강.

**3회차(최대 횟수): needs-attention.** "`fillText`가 Canvas의 유일한 텍스트 그리기 API"라는 전제 자체가 틀림(medium) — Canvas 2D에는 `strokeText`도 있어 이 가정으로는 `strokeText`로 그린 텍스트를 놓칠 수 있음.
→ `06-pipeline.md` §1-1 "재검수 최대 3회" 규칙에 따라 Codex 재호출 없이 즉시 반영: `fillText|strokeText` 결합 검색 명령+결과를 `raw_log.txt`에 추가(두 버전 모두 `strokeText` 0건, `fillText` 건수는 기존과 동일), `result.md`·`report.md`의 "유일한 API" 표현을 "Canvas 2D의 텍스트 그리기 API 둘 다"로 교정.

## 결론
모드B 3차 이후 종료 → 마스터가 Codex의 Recommendation을 그대로 반영(`fillText\|strokeText` 결합 검색). 이번 작업의 핵심 교훈: "전수 검사"를 주장할 때는 (1) 검색 패턴이 변수명이 아니라 API/메커니즘 수준이어야 하고, (2) 그 API 집합 자체가 실제로 전부인지(이번엔 `fillText` 외 `strokeText`를 빠뜨림) 재확인해야 한다 — 두 조건 모두 충족해야 "전수"라는 말을 쓸 수 있다는 게 T2-10의 3라운드에 걸쳐 드러났다. T2-6~T2-9의 "서술 vs 재현 가능한 원자료" 교훈에 "그 원자료가 실제로 전체 집합을 덮는가"라는 한 단계가 추가된 셈.
