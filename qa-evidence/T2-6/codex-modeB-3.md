## `06-pipeline.md` §1-1에 따른 처리

## 반영
1. **로그 종료 경계**: QA가 끝난 뒤 실제로 서버 프로세스를 `Stop-Process`로 종료하고, 종료 후 `curl`이 더 이상 응답을 받지 못함(`post-shutdown status: 000`)을 확인했다. 그 시점까지의 로그(47줄, 프로세스 기동~강제종료 직전 마지막 요청까지)를 `server-log-full.txt`로 교체 — 이제 "로그 이후에 요청이 더 있었을 수 있다"는 의문 자체가 성립하지 않는다(프로세스가 죽었으므로).
2. **재오픈 동일성 주장의 근거 재배치**: REQ-03 핵심 주장("저장→재오픈 동일성")의 **1차 증거**는 수동 관찰이 아니라 `test_save_then_reload_matches`(바이트 단위 assert, pytest 77/77에 포함, 코드로 직접 실행·검증됨)이고, 수동 브라우저 QA는 "이 API 보장이 실제 화면에서도 그대로 동작한다"는 보조 확인임을 result.md에 명시했다. 추가로 QA 원복 뒤의 실제 `GET` 응답 본문을 `response-body-after-cleanup.json`으로 커밋해, 테스트용 노트("1430")가 0건임을 `grep`으로 직접 보일 수 있게 했다.
3. **PracticeCanvas 반영 주장의 범위 축소**: "픽셀 단위로 노트 하나하나를 대조했다"가 아니라 "편집기와 연습 화면이 동일한 API 호출·코드 경로(`fetchSongDrumScore`, DRUMSCORE_EDITED 우선 로직)를 공유함을 코드로, 그리고 화면이 정상 렌더링됨을 스크린샷으로 확인했다"로 주장 범위를 명확히 좁혔다 — 그 이상의 바이트 동일성은 이미 (2)의 자동화 테스트가 담당.

## 결론
3회차 이후 종료 → 마스터가 직접 로그 경계를 닫고(서버 프로세스 실제 종료) 증거 성격(자동 assert vs 수동 관찰)을 명확히 구분해 문서화한 뒤 진행. 이번 모드B 3라운드의 교훈: "자동화 테스트가 이미 바이트 단위로 증명하는 주장"과 "수동 관찰로만 뒷받침되는 주장"을 문서에서 섞어 쓰면, 후자에 대한 의심이 전자까지 끌어내린다 — 핵심 수용 기준(REQ-03의 저장↔재오픈 동일성)은 애초에 수동 QA가 아니라 테스트가 증명하도록 설계했어야 하고(실제로 이미 그렇게 돼 있었다), 문서는 그 사실을 더 먼저, 더 명확히 썼어야 했다.
