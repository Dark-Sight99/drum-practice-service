# T3-45 — 하이햇 검출 개선 레버 실험 결과

## 실험 대상
`음원/pretender.mp4` 1곡, Demucs `stem_drums.wav` 하나에서 시작(세 변형 모두 같은 원본).

## 변형 A — 음량만 올리기
`normalize_loudness()`의 목표 RMS를 운영 기본값(-18dBFS)에서 -12/-8/-4dBFS까지 올려 ADTOF 재실행.

| 목표 RMS | 총 노트 | hihat_closed(GM42) |
|---|---|---|
| -18dBFS(기존) | 703 | 0 |
| -12dBFS | 703 | 0 |
| -8dBFS | 703 | 0 |
| -4dBFS | 703 | 0 |

**4단계 전부 완전히 동일**(노트 수, 스펙트럼 특징까지 소수점 일치). 전체 음량을 14dB 키워도
모델 판단이 전혀 안 바뀜 → **단순 전체 게인 증폭은 이 곡의 하이햇 미검출 원인이 아님**(모델
내부 정규화 레이어 때문으로 추정, 반증 확인).

## 변형 B/C — DrumSep(aufr33-jarredou MDX23C) 6갈래 분리 후 스템별 ADTOF
`stem_drums.wav`를 6스템(kick/snare/toms/hh/ride/crash)으로 분리해, 각 스템을 (B)기존
기본값(-18dBFS)과 (C)변형 A에서 쓴 부스트값(-8dBFS)으로 각각 ADTOF에 **단독** 입력.

| 분리된 스템 | 독립 onset 검출(스템 자체 타격 수) | 스템 RMS | ADTOF 결과(B=C, 동일) |
|---|---|---|---|
| kick | 341 | -41.5dBFS | kick 317 (ground truth와 근접) |
| snare | 302 | -46.8dBFS | snare 59 + **tom_mid 159**(오분류) = 218 |
| toms | 173 | -58.1dBFS | tom_mid 7만(대부분 누락) |
| **hh** | 967 | **-79.6dBFS** | **0건**(전부 0) |
| ride | 994 | -83.2dBFS | kick 401(!) + snare 115 + hihat_closed 35 = 551 |
| crash | 1640 | -80.1dBFS | 0건(전부 0) |

### 핵심 관찰
1. **hh/crash 스템 자체가 매우 조용함(-80dBFS 안팎)** — kick/snare/toms 스템(-41~-58dBFS)보다
   22~38dB나 낮음. DrumSep이 이 곡(실은 Demucs가 한 번 분리한 결과물)에서 하이햇·크래시를
   거의 못 뽑아냈다는 뜻으로 보임. (⚠ 확인 필요: 실제로 들어보거나 스펙트럼을 추가 분석하면
   "진짜 하이햇 소리가 아주 작게라도 있는지" vs "거의 잡음만 남았는지" 더 명확해짐 — 이번
   실험은 RMS·onset 개수까지만 확인했고 음색 검증까지는 안 함.)
2. **음량을 올려도(B→C) 똑같음** — hh 스템을 -8dBFS로 세게 부스트해도 ADTOF 출력은 0건 그대로.
   변형 A와 같은 결론을 다시 한번 확인: 음량이 원인이 아님.
3. **6갈래로 쪼개서 ADTOF에 단독으로 넣는 방식은 하이햇을 전혀 못 살리고, 오히려 다른 악기에서
   새로운 오분류를 만듦**:
   - ride 스템을 ADTOF에 넣으니 401건을 "킥"으로 잘못 분류(라이드는 물리적으로 킥과 전혀
     다른 소리인데도) — ADTOF가 "믹스 전체" 입력을 가정하고 학습된 모델이라, 단일 악기만
     들어오는 입력(분포 밖 입력)에서는 신뢰할 수 없는 출력을 낸다는 뜻으로 해석됨.
   - snare 스템 넣으니 159건이 "탐"으로 오분류.
   - toms 스템 넣으니 173개 중 7개만 잡힘(대부분 누락).

## 결론
- 의뢰인 질문 1(6갈래 다 가져오면 더 정확해지나?) → **이 실험에서는 아니었음.** 오히려 기존
  파이프라인(믹스 전체 → ADTOF)보다 못한 결과(새 오분류 발생). ADTOF를 그대로 둔 채 입력만
  스템 단위로 쪼개는 방식은 비효율적인 것으로 보임 — 작동하려면 ADTOF가 아닌 다른 분류/온셋
  검출 로직이 필요할 가능성이 높음(이번 실험 범위 밖, 별도 설계 필요).
- 의뢰인 질문 2(음량이 작아서 하이햇을 못 잡나?) → **반증됨.** 원곡 전체 음량(변형 A)과
  분리된 하이햇 스템 자체(변형 C) 둘 다 세게 키워봤지만 결과가 전혀 안 바뀜.
- 종합: 이 곡의 하이햇 미검출은 "음량 문제"도 "그냥 믹스에 섞여서 못 찾는 문제"도 아니고,
  DrumSep 분리 단계에서조차 하이햇 신호 자체를 거의 못 뽑아내는 더 근본적인 한계로 보임
  (Q-42와 연결 — field-wide 한계라는 기존 조사 결과와 일치).

## 변형 D/E — 다른 모델로 완전 교체(ADT_STR, Inverse Drum Machine)
의뢰인 요청으로 ADTOF 자체를 다른 모델로 바꿔보는 실험도 같은 1곡(pretender 드럼 스템)으로 추가.

### D. ADT_STR(72.3M 파라미터 Transformer, 합성 데이터 학습, CC BY-SA 4.0, tau=0.6 체크포인트)
ADTOF 대신 이 모델에 드럼 스템을 직접 넣어 MIDI를 바로 뽑음(완전 교체 테스트).

| 피스(GM) | 건수 |
|---|---|
| Acoustic Bass Drum(35) | 106 |
| Bass Drum 1(36) | 235 |
| Acoustic Snare(38) | 221 |
| Side Stick(37) | 5 |
| Hand Clap(39) | 9 |
| Floor Tom(41) | 1 |
| Mid Tom(45) | 5 |
| High Tom(47) | 1 |
| Cowbell(52) 등 기타 | 24 |
| **Closed Hi Hat(42)** | **0** |
| **Crash/Ride/Splash 등 모든 심벌류(46/48/49/51)** | **0** |

총 617노트. 킥 두 클래스 합(106+235=341)이 변형B의 독립 onset 검출로 잰 킥 타격 수(341)와
정확히 일치 — 킥은 잘 잡음. 그러나 **하이햇은 0건, 심지어 크래시/라이드 등 심벌류 전체가
한 건도 없음**. 완전히 다른 아키텍처(합성 데이터로 학습한 Transformer)로 교체해도 이 곡의
하이햇(그리고 모든 심벌)을 전혀 못 잡는다는 뜻.

### E. Inverse Drum Machine(idm-44-train-kits, Apache-2.0)
사실상 분리기(변형B/C의 DrumSep과 같은 성격) — `separate()`로 9클래스(HH_CHH/HH_OHH 포함)로
드럼 스템을 분리.

| 분리된 스템 | 독립 onset 검출 | RMS |
|---|---|---|
| KD(킥) | 55 | -52.9dBFS |
| SD(스네어) | 128 | -57.3dBFS |
| TT_HFT(하이플로어탐) | 559 | -41.6dBFS(제일 큼, 의심스러움) |
| TT_HMT | 10 | -64.2dBFS |
| TT_LMT | 154 | -53.5dBFS |
| **HH_CHH(닫힌 하이햇)** | **0** | **완전 무음** |
| **HH_OHH(열린 하이햇)** | **0** | **완전 무음** |
| CY_CR/CY_RD(크래시/라이드) | 0 | 완전 무음 |

DrumSep보다 더 극단적 — 하이햇·심벌 스템이 완전히 무음(DrumSep은 "매우 조용함"이었지
"전혀 없음"은 아니었음). 킥 건수(55)도 독립 onset 기준 다른 방법들의 킥 건수(300대)에 비해
너무 적고, 탐 하나(TT_HFT)에만 비정상적으로 몰려있어(559건, 다른 모든 스템보다 큰 RMS) —
이 모델(`idm-44-train-kits`, 아마 특정 스튜디오 드럼킷 녹음으로 학습)이 이 곡의 음향 특성과
안 맞아 분리 자체가 깨진 것으로 보임(확인 필요: 다른 체크포인트나 다른 곡으로 재검증 전까지는
"이 체크포인트가 이 곡엔 안 맞는다" 수준의 결론만 가능).

### D/E 종합
**서로 완전히 다른 아키텍처(기존 ADTOF, DrumSep+ADTOF, ADT_STR, IDM) 4가지 전부**가 이 곡에서
하이햇(과 대부분 심벌)을 거의 또는 전혀 못 잡는다는 같은 결론으로 수렴함 — 이제 "특정 모델
하나의 버그"라기보다 (a) 이 녹음의 하이햇/심벌 음향 특성 자체가 유난히 어렵거나, (b) 테스트한
모델들이 공통으로 기대하는 입력 분포(원본 스테레오 믹스, 또는 특정 스튜디오 녹음 방식)와
우리가 실제로 넣는 입력(Demucs로 한 번 분리된 "드럼 전체" 스템)의 차이 자체가 공통 원인일
가능성이 더 높아 보임(둘 다 확인 필요, 추측 명시).

## 변형 F — ADTOF 원시 활성값(임계값 이전) 직접 확인 — 결정적 근거
"혹시 임계값(threshold)이 너무 높아서 그런 거 아닐까?"를 직접 확인. ADTOF-pytorch는 각
GM 클래스마다 0~1 사이 활성값을 프레임별로 내고, 그 값이 클래스별 임계값(하이햇 0.22,
크래시 0.30, 킥 0.22, 스네어 0.24, 탐 0.32)을 넘을 때만 노트로 확정한다. 315초 전체
프레임의 **원시 활성값**(임계값 적용 전)을 뽑아봄:

| 클래스 | 운영 임계값 | 전체 곡 중 **최댓값** | 99.9퍼센타일 |
|---|---|---|---|
| 킥 | 0.22 | 0.777 | 0.706 |
| 스네어 | 0.24 | 0.865 | 0.664 |
| 탐 | 0.32 | 0.797 | 0.687 |
| **하이햇** | **0.22** | **0.125** | 0.039 |
| **크래시** | **0.30** | **0.008** | 0.003 |

킥·스네어·탐은 임계값을 훌쩍 넘는 구간이 자주 있어 정상 검출됨. **하이햇은 315초 전체에서
단 한 순간도 0.15를 넘은 적이 없고(최댓값 0.125), 크래시는 거의 0(최댓값 0.008)** — 즉
"임계값이 너무 엄격해서 놓친다"가 아니라 **모델이 애초에 이 곡의 하이햇·크래시를 "그럴듯하다"고
느끼는 순간이 단 한 번도 없다**는 뜻. 임계값을 0.05까지 극단적으로 낮춰도(노이즈를 전부
하이햇으로 오인할 위험을 감수하고도) 하이햇 활성화 프레임은 전체의 0.07%뿐이고 크래시는
0%. **임계값 조정으로는 해결 불가능 — 확정.**

## 종합 결론(변형 A~F 전체)
서로 독립적인 **6가지 레버**(음량↑, 6갈래분리 2종, 모델교체 2종, 임계값) 전부가 이 곡의
하이햇을 못 살림. 특히 변형 F가 "왜"에 대한 가장 직접적인 답 — 모델 내부적으로 확신도 자체가
없음(threshold 문제가 아니라 feature/representation 문제). 외부 연구 조사(ADTOF Plus
저자의 벤치마크, STRUM 논문 등)도 종합하면: (1) 격리된 스템 vs 원본 믹스 입력 차이는
하이햇/심벌에는 큰 영향이 없다고 보고됨(ADTOF Plus 벤치마크, MDB 기준 0.863→0.858), (2)
현재 연구 최전선 시스템(STRUM, 6개 분류기 앙상블+휴리스틱)조차 크래시·라이드 레인 정확도가
0.19~0.57 수준 — "거의 완벽한" 자동 하이햇/심벌 검출은 지금 기술 수준에서 달성 가능한
목표가 아님. 즉 이번 곡(그리고 비슷한 성격의 다른 곡들)에서 하이햇을 100% 자동으로 잡는 건
현실적인 목표가 아니고, "최선을 다한 자동 채보 + 빠른 수동 보정"을 제품 설계의 전제로 삼는
쪽이 맞다고 판단됨.
