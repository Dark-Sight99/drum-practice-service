# T3-69 결과

## 배경 (의뢰인 요청, 2026-10-29)
두 가지 요청/버그 제보:
1. "편집흔적이 있는데 저장버튼 누르지 않고 라이브러리나 연습화면으로

2. "저장버튼이 처음에는 비활성화 되어있는데 어느지점에 노트를 한 번
   찍고 실행취소를 눌러서 처음과 실제 바뀐건 없는데 저장버튼은
   활성화가 되어있더라... 여러 노트를 찍었다가 실행취소로 최초상태로
   돌렸음에도 저장버튼이 활성화가 되어있다."

## 조사 — "노트 찍고 실행취소" 재현 시도
실제 로그인 환경(QA_AI 계정, 의뢰인이 업로드해준 실제 곡)에서 똑같이
"클릭으로 노트 1개 생성 → 실행취소 1번", "노트 3개 생성 → 실행취소
3번"을 재현해봤는데, **두 경우 다 저장 버튼이 정확히 비활성화로
돌아왔다**(`isDirty`는 "저장 시점 객체 참조와 지금 참조가 같은지"로
판정하는데 — EditorScreen.tsx의 기존 주석 참고 — `editHistory.ts`의
`undo()`가 과거 스택에 저장해둔 바로 그 객체 참조를 그대로 복원하므로,
커밋 횟수와 실행취소 횟수가 1:1로 맞으면 이 메커니즘 자체는 정확했다).
`EditorScreen.test.tsx`에도 이미 이 정확한 시나리오(노트 1개 + 실행취소
1번)를 검증하는 테스트가 있었고 계속 통과하고 있었다.

재현에는 실패했지만, 코드를 읽다가 **같은 증상을 내는 다른 실제
버그**를 발견했다: `updateSelectedNote()`(셈여림·손·HH 닫힘/열림 전환·
화살표 키 이동이 전부 거치는 공통 경로)가 patch를 적용한 뒤 값이
실제로 달라졌는지 전혀 확인하지 않고 항상 `commit()`을 호출했다.
그래서:
- 이미 "중"으로 선택된 노트에 "중" 버튼을 또 누르거나,
- 화살표 키로 이동시키려는데 이미 격자 왼쪽 끝(틱 0)이라
  `Math.max(0, ...)`로 제자리에 클램프되는 경우,

값은 그대로인데도 매번 "새로운" 상태 객체가 history에 밀려 들어가
저장 버튼이 켜졌다. 의뢰인이 겪은 정확한 "노트 찍고 실행취소" 순서와는
다르지만(그 경로는 재현 결과 정상이었음), "실제로 안 바뀌었는데 저장
버튼이 켜진다"는 같은 증상 범주의 확인된 실제 버그라 같이 고쳤다.
**의뢰인이 겪은 정확한 순서를 다시 보게 되면 알려주시면 좋겠다** —
위 테스트로는 재현이 안 돼서, 드래그를 살짝 같이 했는지, 셈여림/손
버튼을 같이 눌렀는지 등 추가 단서가 있으면 더 정확히 좁힐 수 있다.

## 구현

### 1. 나가기 전 저장 확인 모달 (REQ-03)
"← 라이브러리"·"← 연습 화면" 버튼을 바로 `onCancel`/`onBackToPractice`로
연결하던 걸 `requestLeave()`로 감쌌다 — `isDirty`가 false(흔한 경우,
바뀐 게 없음)면 기존처럼 바로 이동하고, true면 기존 `components/Modal.tsx`
(T3-19부터 쓰던 범용 모달 — 배경 클릭·Esc로 닫힘)로 "저장하지 않은
변경사항... 저장할까요?"를 띄우고 3개 선택지를 준다:
- **취소**: 모달만 닫고 화면에 남는다(편집 내용 그대로 유지).
- **저장 안 함**: 저장하지 않고 원래 가려던 곳으로 그대로 이동(기존
  "임의로 버리고 이동" 동작 그대로, 그냥 확인을 한 번 거칠 뿐).
- **저장**: 실제로 저장한 뒤 원래 가려던 곳으로 이동.

`handleSave()`를 "저장 성공 시 boolean만 돌려주는" 함수로 바꿨다(기존엔
성공하면 그 안에서 바로 `onSaved()`를 불러 **항상 라이브러리로
이동**했는데, 그러면 "연습 화면으로 나가려다 모달에서 저장"을 선택한
경우에도 라이브러리로 잘못 보내게 된다 — 저장 성공 후 어디로 갈지는
호출한 쪽이 결정하게 분리했다). 툴바의 기존 "저장" 버튼은
`handleSave().then(ok => ok && onSaved())`로 바뀌어 기존과 동일하게
항상 라이브러리로 이동한다(동작 변화 없음). 저장이 실패하면(검증
오류·서버 오류) 모달만 닫고 화면에 남아 기존 저장 실패 에러 메시지가
그대로 보인다(저장 버튼을 다시 누르거나 "저장 안 함"으로 포기 가능).

### 2. 값이 실제로 안 바뀌면 커밋하지 않음(REQ-03)
`updateSelectedNote()`에 패치 적용 후 tick·piece·velocity·hand·
handSource 5개 필드를 기존 선택된 노트와 비교해 하나도 안 바뀌었으면
`commit()`을 호출하지 않고 그냥 리턴한다. 이 함수 하나가 셈여림(약/중/
강)·손(R/L/RF/LF)·HH 닫힘/열림 전환·화살표 키 이동(moveSelected)의
공통 경로라 한 곳만 고치면 전부 해결된다.

## 브라우저 QA
실제 로그인 환경(QA_AI 계정, 의뢰인이 업로드해준 실제 곡)에서 직접
확인(저장 안 누르고 "저장 안 함"으로 나가 원본 곡 데이터는 그대로):
- 노트 1개 생성 후 "← 라이브러리" 클릭 → "저장하지 않은 변경사항...
  저장할까요?" 모달이 정확히 뜸(스크린샷 확인).
- "취소" 클릭 → 모달만 닫히고 편집 화면에 남음, 저장 버튼 여전히 활성
  (편집 내용 보존) 확인.
- "저장 안 함" 클릭 → 라이브러리로 정상 이동, 원본 곡에는 영향 없음
  (저장 API 호출 자체가 없었음) 확인.
- "노트 찍고 실행취소" 재현 시도(위 "조사" 참고) — 1개/3개 모두 정상
  (저장 버튼 비활성화)이라 이 버그는 **재현 못 함**, 대신 발견한
  no-op 커밋 버그는 코드 경로가 명확해 단위 테스트로 검증.

## 남은 작업
- 의뢰인이 다시 "노트 찍고 실행취소했는데 저장 버튼이 안 꺼진다"를
  겪으면, 그 직전에 드래그·셈여림/손 버튼 클릭 등 다른 조작이 같이
  있었는지 알려주시면 좋겠다 — 이번 no-op 커밋 수정이 실제로 그
  경우였다면 이미 해결됐겠지만, 재현에 실패해 100% 확신은 못 함.
- 실제 로그인 후 모달의 "저장" 버튼(저장하면서 나가기) 경로까지는
  이번에 직접 확인 못 함(단위 테스트로는 확인) — 필요하면 다음에 QA_AI
  계정으로 추가 확인 가능.
