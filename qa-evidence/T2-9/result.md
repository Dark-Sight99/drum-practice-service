## 판정 순간 정밀도 수정
`render/laneRenderer.ts`의 노트 도형을 `yCenter - shapeBottomExtent(shape, noteSize)`에 그리도록 수정(**최종 구현** — 1차 수정은 모든 도형에 `noteSize/2`를 일괄 적용했으나, Codex 모드A가 `x-ring`(열린 하이햇, 실제 그려지는 반지름이 `noteSize*0.75`로 다른 도형보다 큼)에서 어긋난다고 지적해 도형별 실제 하단 돌출 거리를 계산하는 `shapeBottomExtent()`로 교체함 — `x`/`diamond`/`circle`=half, `x-large`=half*1.3, `x-ring`=half*1.5, `rounded-rect`=size*0.35, `circle-large`=half*1.2, `bar`=size*0.2) — 도형의 **실제로 그려지는 하단 모서리**가 판정선에 닿는 순간이 노트의 계산된 시각(=실제 소리 재생 시각, T2-8에서 이미 맞춰둠)과 일치하게 됨. 이 수정은 노트의 **시각(초) 계산**(`noteTimeOf`, 판정창 `hitWindowSeconds`)을 전혀 안 건드리고 이미 올바른 시각에 그려지는 도형의 **그리는 좌표만** 도형별 상수(8~21px)만큼 이동한 것이라 "오디오 타이밍·동기" 위험 작업이 아님(시각 자체가 아니라 그 시각을 화면의 어느 픽셀에 대응시키는지만 바뀜) — Codex 모드C 생략, T2-7의 표시 전용 변경과 같은 패턴. 실제 브라우저로 재생해 도형이 판정선 부근에서 하단부터 닿는 모양을 스크린샷으로 확인(`screenshot-edge-fix-playback.jpg`, 1차 수정 적용 시점 캡처) — 정확한 프레임(도형 바닥이 선에 닿는 그 한 프레임)을 포착하는 건 스크린샷 타이밍 도구의 한계로 보장 못 하므로, 코드 자체의 상수 오프셋 정확성(리뷰로 확인 가능, `shapeBottomExtent()`가 `drawNoteShape()`의 실제 그리기 범위와 1:1 대응함은 코드 대조로 확인됨)이 1차 근거이고 스크린샷은 보조. 수정 후 재생 스크린샷은 별도로 다시 캡처하지 않음(도구로 정확한 접촉 프레임을 포착하는 보조 증거의 한계 때문에 추가 캡처의 증거 가치가 낮다고 판단 — 핵심 근거는 코드 리뷰).

## MusicDelta_Grunge 출처 — 새 버그가 아니라 테스트 데이터 선택 문제
사용자가 보고한 "초반 노트가 실제 음과 전혀 다름", "중간에 소리가 잠깐 사라짐"의 원인을 찾기 위해 이 곡의 원본 MIDI 출처를 조사:
- `data/songs/2/original.mid`(실제 업로드된 곡 파일)와 `data/t0-2-work/MusicDelta_Grunge.mid`(Phase 0, T0-2 ADTOF 드럼 채보 모델 평가 파이프라인의 산출물 — `qa-evidence/T0-2/eval_adtof.py`의 `full_mix.wav --[Demucs separate]--> drums.wav --[adtof-pytorch]--> output.mid` 과정 결과)를 `xxd`로 바이트 단위 비교 — **완전히 동일**함을 확인. 즉 지금 라이브러리의 "MusicDelta_Grunge"는 사람이 만든 정답 MIDI가 아니라 **AI 모델이 실제 드럼 음원을 듣고 자동으로 받아쓴 결과물**이다.
- `qa-evidence/T0-2/result_raw.json`에 이미 측정돼 있던 이 트랙의 분류별 F-measure(`musicdelta-grunge-fmeasure.json`에 원문 보존): 킥 0.97(거의 정확), 스네어 0.85, **탐(TT) 0.33**(정밀도 0.5·재현율 0.25 — 실제 탐 12건 중 모델이 찾아낸 건 겨우 3건(`n_est`), 그나마도 절반은 오탐). 재현율 0.25는 "실제 탐 히트의 75%가 MIDI에 아예 없다"는 뜻이다.
- **인과관계 표현을 Codex 모드B 지적대로 한정**: 위 F-measure는 **곡 전체 평균** 수치이지 사용자가 지적한 "초반 구간"·"중간의 특정 소리 끊김 구간"이 정확히 그 누락·오탐 지점과 같다는 것까지 구간 단위로 대조해 증명한 것은 아니다. "모델이 이 트랙에서 탐을 다수 놓치는 걸로 측정돼 있다"는 사실과 "사용자가 보고한 증상의 성격(소리가 사라짐·음이 다름)이 그런 종류의 오류와 같은 범주"라는 **정황상 설명**까지만 주장하고, "이 특정 순간이 바로 그 누락이다"는 구간 단위 인과 확정은 하지 않는다(그러려면 실제 재생 중 어느 틱에서 증상이 나는지와 해당 틱의 MIDI 이벤트를 대조해야 하는데, 이번 작업에선 하지 않았다).
- **결론**: MusicDelta_Grunge의 MIDI가 사람이 만든 정답이 아니라 AI 모델이 자동 채보한 것이고, 그 모델의 해당 트랙 정확도가 Phase 0에서 이미 낮게 측정돼 있었다(특히 탐)는 것은 바이트 비교+기존 기록으로 **확정**된 사실이다. 사용자가 보고한 구체적 증상이 정확히 그 누락 지점과 일치하는지는 **미확인**이며, T2-x 구현에 실제 재생 경로 버그가 남아있을 가능성 자체를 이 조사가 배제하지는 못한다 — 다만 발견된 동기화 버그(T2-8)와 판정 정밀도(T2-9 본 작업)는 이미 수정했고, 남은 "노트가 실제 음과 다름" 호소의 상당 부분이 데이터 품질(ADTOF 한계)로 설명 가능하다는 것까지가 이번 조사의 범위다.
