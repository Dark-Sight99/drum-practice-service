모드: C
판정: 수정 후 진행
요약: 계획의 큰 흐름은 타당하지만, 업로드 파일명 처리·DrumScore의 서버 검증·쿠키의 운영 환경 가정이 정해지지 않아 그대로 구현하면 안전성과 REQ-07 수용 기준을 보장하기 어렵습니다.

필수 수정:

- C-001 [work/T2-5/plan.md §설계 1] `write_song_file(song_id, filename, content)`가 전달받은 파일명을 어떻게 안전한 경로로 바꾸는지 계획에 없습니다. `resolve_asset_path()`의 `resolve()`와 `is_relative_to()` 검사는 **DB에 저장된 경로를 읽을 때**의 방어이며, 파일을 쓰는 단계의 경로조작을 막아주지 않습니다. `Asset`의 CheckConstraint도 보조 방어일 뿐이라고 모델 주석이 명시합니다. 업로드 원본 파일명은 신뢰하지 말고 서버가 고정 파일명 또는 안전한 basename을 생성하며, 쓰기 전에도 최종 경로가 `SONGS_ROOT` 아래인지 확인하도록 설계에 추가하십시오. 근거: `app/server/db/models.py`의 `Asset` CheckConstraint 주석, `app/server/db/session.py`의 `PROJECT_ROOT` 계산 방식.

- C-002 [work/T2-5/plan.md §4] 서버가 DrumScore의 구조만 검사하고 의미 검증을 생략하는 결정은 이 규모에서도 타당하다고 보기 어렵습니다. 로그인은 호출자의 신원만 확인하며, 브라우저가 보낸 JSON이 유효한 점수인지 보장하지 않습니다. 의미가 잘못된 점수가 DB와 파일에 저장되면 이후 재생·편집 단계가 잘못된 값을 처리해야 합니다. 특히 REQ-02는 세 입력 경로가 같은 DrumScore 형식으로 수렴해야 합니다. 서버에서 가능한 핵심 불변식(수치의 유한성·범위, 박자·PPQ·노트 필드와 값의 유효성)을 검증하고, 클라이언트 검증은 편의용으로 취급하도록 경계를 명시하십시오.

- C-003 [work/T2-5/plan.md §3·QA 계획] 쿠키 설정을 고려하지 않아 REQ-07의 여러 기기 접근을 보장하지 못합니다. 기존 `app/server/api/auth.py`는 로그인 쿠키에 `secure=True`를 설정합니다. Vite 프록시는 브라우저 요청을 같은 출처처럼 보이게 하지만, 쿠키의 Secure 조건까지 없애지는 않습니다. 로컬 HTTP와 홈서버/Tailscale 접속에서 실제 접속 URL이 HTTPS인지, 해당 환경에서 로그인 쿠키가 저장·전송되는지 계획에 정하고 검증해야 합니다. HTTPS가 아닌 배포를 지원한다면 안전한 HTTPS 제공 방안 또는 환경별 쿠키 정책을 설계에 포함하십시오.

권장 사항:

- C-004 [work/T2-5/plan.md §설계 2] 업로드 도중 파일 저장 또는 DB 커밋이 실패할 때의 정리 순서를 정하십시오. 곡 레코드 롤백만으로는 이미 디스크에 쓴 파일이 정리되지 않을 수 있습니다. 임시 파일에 먼저 쓴 뒤 DB 커밋 후 확정하거나, 실패 시 파일을 정리하는 보상 처리를 계획하는 편이 일관성을 높입니다.

- C-005 [work/T2-5/plan.md §범위·QA 계획] 목록 조회와 DrumScore 조회는 계획되어 있지만, REQ-07의 PC 업로드→폰 재생 기준을 충족할 재생 데이터와 저장소 공유 조건이 불명확합니다. 폰이 같은 서버의 목록·DrumScore에 접근할 수 있는지, 서버가 재시작되어도 `data/songs/`가 유지되는지, 재생 화면이 해당 DrumScore를 받아 실제 재생에 쓰는지 확인 기준을 명시하십시오. 현재 QA의 "다른 기기" 항목은 서버 세션 공유를 확인할 뿐, 실제 폰 접속·재생 경로를 충분히 고정하지 않습니다.

- C-006 [work/T2-5/plan.md §설계 2·3] `PATCH`·삭제·DrumScore 조회의 소유자 검사를 각 API에서 수행한다고 명시하십시오. REQ-08은 계정 간 데이터 분리를 요구하며, 기존 목록/상세 API의 동작만으로 신규 엔드포인트의 검사를 보장할 수 없습니다.

리스크/전략 의견:

- C-007 [work/T2-5/plan.md §설계 3] 화면 네 개에 App 상태 전환을 쓰는 것은 이번 범위에서는 합리적입니다. 다만 URL·뒤로 가기·새로고침·직접 링크가 필요한 화면이 생기면 상태 전환만으로는 복원과 탐색 처리가 어려워질 수 있으므로, 화면 상태를 앱 내부 전환으로 한정한다는 선택을 기록해 두는 편이 좋습니다.

- C-008 [work/T2-5/plan.md §설계 2] "DB 먼저 커밋 후 파일 삭제"는 고아 DB 레코드가 끊긴 파일을 가리키는 상황을 줄이는 선택으로 타당합니다. 다만 파일 삭제 실패 시 고아 파일이 남는 것은 허용하는 정책이므로, 로그 기록과 재시도 또는 정리 방법을 정해 두십시오.

확인하지 못한 것: 지정된 기존 `app/server/api/auth.py`, `app/server/db/models.py`, `app/server/db/session.py`, `app/web/vite.config.ts` 및 현재 화면 파일은 읽었습니다. 계획에서 참조한 T2-1의 파서·DrumScore 검증 구현, T2-3/T2-4 재생 연결, 운영 배포의 HTTPS·저장소 지속성 설정은 검수 범위에서 확인하지 못했습니다. 파일 쓰기나 테스트는 실행하지 않았습니다.
