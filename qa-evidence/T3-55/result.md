## 구현

### 1) 서버다운 시 "Bad Gateway" 영어 원문 노출 (`app/web/src/api/client.ts`)
`readErrorMessage()`가 JSON 바디 파싱에 실패하면(Vite 프록시·리버스
프록시의 기본 에러 페이지 등 — FastAPI 자신이 아님) `response.statusText`를
그대로 썼다. 502/503/504(게이트웨이류 — "지금 서버에 연결 안 됨"이라는 뜻은
누가 보내든 같음)일 때만 공통 한글 문구("서버에 연결할 수 없습니다. 잠시
후 다시 시도해주세요")로 대체 — FastAPI 자신이 의미 있는 한글 detail을
JSON으로 보내는 502/503 응답은 여전히 그 메시지를 그대로 쓴다(상태 코드
우선이 아니라 JSON 파싱 성공 여부를 먼저 봄). 이 수정은 apiFetch 공용
함수 하나라 로그인뿐 아니라 모든 API 호출에 똑같이 적용됨.
실배포 환경(리버스 프록시 유무·종류)과 무관하게 안전 — 502/503/504이면
항상 친절한 문구로 바뀌므로 "모른다"로 남겨뒀던 배포 환경 질문 자체가
더 이상 문제되지 않음.

### 2) 음원 트랙 다운로드 실패 — 재시도 (`PracticeCanvas.tsx`)
`createAudioTrackPool()` 실패 시 조용히 신스 드럼 폴백으로 넘어가던 것에
`audioTracksFailed` 상태를 추가. 실패하면 재생 버튼 아래(블루투스 안내문과
같은 폭·위치)에 "음원을 불러오지 못해 신스 드럼으로 재생합니다. [다시 시도]"
배너를 상시 노출. "다시 시도"는 `audioTracksRetryToken`을 올려 기존
`useEffect`(songId/availableAudioKindsKey에 의존)를 다시 돌게 해 풀 생성을
재시도 — 새 로직 없이 기존 cancelled 가드·cleanup을 그대로 재사용. 재생
자체는 여전히 막지 않음(신스 폴백 유지 — 의뢰인 지적대로 "드럼 소리만
나는" 상태지만, 적어도 왜 그런지는 알 수 있고 바로 재시도 가능).

### 3) 재생 시작 실패 — 재시도 (`PracticeCanvas.tsx`)
`handlePlay()`의 catch 블록이 `cleanupAbortedSetup()` 후 `throw err`로
다시 던졌는데, 호출부(`onClick={handlePlay}`, `void handlePlay()`) 어디도
안 받아 처리되지 않은 Promise 거부로 콘솔에만 남았다. 위 오디오 트랙 풀
실패와 같은 패턴(콘솔 로그 + 상태 플래그)으로 바꿔 `playStartFailed`를
세우고, 같은 자리에 "재생을 시작할 수 없습니다. [다시 시도]" 배너.
"다시 시도" 버튼은 `handlePlay`를 그대로 다시 호출 — 처음 재생 버튼을
누르는 것과 완전히 같은 경로(새 세션 셋업을 처음부터)라 별도 로직 불필요
(의뢰인 질문 3에 대한 답 그대로). `handlePlay()` 진입 시(재시도 포함)
맨 앞에서 `playStartFailed`를 false로 리셋해 재시도 중엔 배너가 사라짐.

### 4) 전역 에러 바운더리 (`components/ErrorBoundary.tsx`, `main.tsx`)
`componentDidCatch`/`ErrorBoundary` 검색 결과 0건으로 전역 안전망이
전혀 없음을 확인. 클래스 컴포넌트로 새로 작성해 `main.tsx`에서 `<App />`
전체를 감싼다. 렌더링 중 예외가 나면 "문제가 발생했습니다" 카드 +
[다시 시도](새로고침 없이 자식 트리만 다시 그려봄, state만 리셋)/
[새로고침](`window.location.reload()`, 하드 리로드) 두 버튼. 애초
목업에서 제안했던 "라이브러리로" 버튼은 — 이 앱이 URL 라우팅 없이
App.tsx 내부 상태로만 화면을 전환하는 구조(work/T2-5/plan.md §설계 3)라
크래시 후엔 그 상태 자체가 날아가 있어 "라이브러리로"와 "새로고침"이
사실상 동일 동작이 되므로, 대신 "다시 시도"(네트워크 재요청 없이 더
가벼운 복구 시도)로 바꿔 두 버튼이 실제로 다른 걸 하게 했다.
