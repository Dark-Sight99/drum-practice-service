# T3-16-feedback-5(장기 캐시 헤더) QA 결과

## 근거(REQ)
REQ-04/05. T3-16-feedback-4(프리페치) 적용 후에도 의뢰인이 맥에서 "많이 좋아졌지만 가끔 남는다"고 재확인, 더 개선 요청.

## 배경 (코드로 확인)
`GET /songs/{id}/audio/{kind}`(Starlette `FileResponse`)는 기본적으로 `etag`/`last-modified`만 설정하고 `Cache-Control`은 전혀 안 보냄(소스 직접 확인) — 브라우저가 매번 서버에 재검증 왕복을 해야 함. 이 파일이 "안전하게 오래 캐시해도 되는지"는 추측 대신 코드로 확인: `app/server/api` 전체에서 `JobType.SEPARATE`를 큐에 넣는 곳은 `upload_audio()`(새 `Song` 생성 시) 딱 한 곳뿐 — 기존 곡을 재분리해 같은 경로를 덮어쓰는 엔드포인트 자체가 없음.

## 변경 내용 (`app/server/api/songs.py`, `tests/test_songs_audio.py`)
1. **1차 구현**: `Cache-Control: private, max-age=31536000, immutable`(1년) 추가.
2. **Codex 모드A 지적(필수, 반영함)**: `private`는 "공유 캐시 금지"일 뿐 "로그인한 이 브라우저의 로컬 캐시"엔 그대로 남는다(RFC 9111 §5.2.2.7). 관리자가 계정을 정지하면 "다음 요청부터 바로" 막혀야 한다는 기존 요구(REQ-08, `wiki/architecture.md`)와 충돌 — 1년치 캐시가 남아있으면 로그아웃·정지 후에도 이미 캐시된 오디오는 계속 재생될 수 있음. **`max-age=3600`(1시간)으로 줄이고 `immutable`은 제거** — 한 연습 세션 동안은 재검증 없이 캐싱 효과를 유지하면서, 정지 뒤 노출 창을 1시간으로 제한.

## ⚠ 추가로 발견한 더 근본적인 한계 (의뢰인 실측)
의뢰인이 Safari 네트워크 탭으로 재측정 — **프리페치(`fetch()`, PracticeCanvas.tsx)는 두 번째 호출부터 디스크 캐시에서 응답을 받아오는 게 확인됐지만(의도대로 동작), 정작 재생 버튼을 눌렀을 때 `<audio>` 엘리먼트가 만드는 Range 요청은 그 캐시를 전혀 재사용하지 않고 4트랙 전부 처음부터 다시(`바이트 범위 0-5268208`, 각 1.5~2초) 받았음.**

원인으로 추정(아직 코드 수정으로 검증 전): 브라우저의 미디어 엘리먼트(`<audio>`/`<video>`)는 일반 `fetch()`/XHR이 쓰는 HTTP 디스크 캐시와 **별도의 미디어 전용 로딩 경로**를 쓰는 경우가 많음 — `fetch()`로 캐시를 데워도 그 뒤에 새로 만들어지는 `<audio>` 엘리먼트의 Range 요청은 그 캐시를 모름. 이게 사실이면 T3-16-feedback-4(프리페치)·이번 작업(Cache-Control)의 네트워크 왕복 감소 효과가 **실제 재생 경로엔 거의 전달 안 되고 있다**는 뜻 — 체감 개선은 주로 다른 요인(압축 자체, iOS 전용 Web Audio 수정)에서 온 것으로 재해석해야 함.

진짜 해결하려면 재생 버튼을 누를 때마다 `createTrackPlayer()`가 새 `<audio>` 엘리먼트를 만드는 지금 구조 대신, 화면 진입 시 만든 엘리먼트를 재생 세션 간에 **재사용**해야 버퍼링된 내용이 유지될 걸로 보임 — 다만 이건 T3-6/T3-9 등에서 다져온 재생 세션 상태 관리(재진입 가드, 정리 로직)를 건드리는 꽤 큰 변경이라, 진행 여부를 의뢰인에게 별도로 확인 중(이 작업 범위 밖).
