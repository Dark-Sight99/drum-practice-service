# T0-3 추가 — oemer(딥러닝 OMR) 비교 실험(2026-10-28)

## 배경
의뢰인이 "음원 자동채보(T3-45) 대신 악보를 정확히 입력받는 방향"을 제안하며, 전통적
규칙기반 OMR(Audiveris, T0-3)보다 최신 딥러닝 기반 OMR이 이 비표준 표기(선생님이
초보자용으로 단순화한 한 줄 압축 표기, 스템 방향으로 하이햇/킥·스네어 구분)를 더 잘
인식하는지 확인 요청.

## 환경 이슈(해결 과정, 참고용)
oemer를 정상 실행하기까지 3가지 환경 문제를 순서대로 발견·수정함(운영 코드와 무관,
`work/T0-3-oemer-comparison/`에서만 사용):
1. onnxruntime-gpu 1.31.1(최신) — 모델 그래프의 ConvTranspose 음수 패딩을 거부함
   → 1.19.2로 다운그레이드(numpy2 호환 유지하면서 거부 전 버전)
2. OpenCV(cv2)가 한글 경로(`C:\...\드럼연습서비스\...`)의 이미지 파일을 못 읾음(Windows
   cv2.imread 비유니코드 경로 한계로 추정) → 영문 경로(세션 스크래치패드)로 이미지 복사
3. opencv-python-headless 5.0.0(2026년 막 나온 메이저 버전) — oemer가 기대하는 4.x API와
   달라 스태프라인 추출 로직이 깨짐 → 4.10.0.84로 다운그레이드

## 실행
```bash
oemer <사진> -o <출력폴더>
```
T0-3과 동일한 21장(`data/samples/sheets_rotated/IMG_7943~7963.jpg`) 전부 실행.

## 결과

| 구분 | 건수 |
|---|---|
| 내부 크래시(출력 파일 0개) | 18/21 (86%) |
| 크래시 없이 MusicXML 생성 | 3/21 (14%) — IMG_7947, 7954, 7963 |

크래시 유형: 17건은 `staffline_extraction.py`의 `IndexError: too many indices for array:
array is 1-dimensional, but 2 were indexed`(스태프라인 검출 로직이 이 압축 표기의 오선
구조를 기대와 다르게 인식), 1건은 `build_system.py`의 `AssertionError: 4`(드럼 보표는
항상 2성부라는 내부 가정이 깨짐 — 이 표기는 보이스가 2개보다 많게 감지됨).

**크래시 안 난 3장도 전부 쓸모없음** — 셋 다 퍼커션 클레프가 아니라 일반 G(치료블) 클레프로
인식했고, 악기 이름이 전부 **"Piano"**(문자 그대로 피아노)로 붙었으며, 생성된 MusicXML
전체에 "percussion"이라는 단어가 단 한 번도 안 나옴. 실제 노트도 하이햇/킥/스네어 구분
없이 임의의 피아노 음높이(예: `<step>D</step><octave>6</octave>`)로 뽑힘.

**→ 21장 중 드럼 노트로 쓸 수 있는 결과: 0장(0%).**

## 결론
- 이 **비표준 표기법(선생님이 만든 한 줄 압축 표기)** 자체가 OMR 도구 대부분(전통 규칙기반,
  딥러닝 기반 둘 다)이 기대하는 표준 드럼 보표와 너무 달라, 둘 다 사실상 못 씀 — 다만 둘
  사이에서는 **Audiveris가 더 낫다**(최소 크래시 없이 처리하고 40%는 퍼커션으로라도 인식).
- oemer 자체는 일반 피아노/멜로디 악보에는 더 나을 수 있음(미검증, 표준 드럼 보표로는
  테스트 안 함) — 하지만 지금 가진 실제 샘플(이 선생님 표기법)에는 전혀 안 맞음.
- "악보를 입력받아 100% 정확한 노트를 만들자"는 방향은, **사진 OMR 경로로는** 현재 가진
  실제 악보 샘플 기준 여전히 비현실적 — Phase 4를 드롭했던 2026-10-26 판단과 일치하는
  결과.
