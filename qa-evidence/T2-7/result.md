## 수동 QA(실제 브라우저 + 실제 FastAPI 서버)
Vite dev(5173) → `/api` 프록시 → 실제 `uvicorn`(127.0.0.1:8000)로 확인. 실제 사용자 곡 "MusicDelta_Grunge"(song_id=2)로 진행 — 모든 편집은 검증 후 원상복구했다(아래 "정리" 항목이 최종 상태를 독립적으로 재검증). 서버 접근 로그 전체(서버 기동~QA 종료 후 프로세스 종료까지, 21줄, 필터링 없음)를 `server-log-full.txt`로 남겼다: `PUT`이 정확히 3건 기록돼 있다(12·17·19행). **이 로그는 요청 본문·호출 주체를 남기지 않아 각 PUT을 어느 조작에 귀속시키는지까지는 로그만으로 증명되지 않는다** — 아래 서술(저장 버튼 1건 + 정리용 콘솔 호출 2건, 후자는 1차 스크립트의 ASI 문법 실수로 같은 요청이 두 번 나간 것)은 수행 당시의 기억에 기반한 설명이며, 건수(3건)와 최종 데이터 상태(아래 "정리")만 로그·응답 본문으로 독립 검증됐다.

1. **편집기 진입**: 기존 곡을 열면 상단 툴바에 "필인 시작손"(오른손/왼손 select) + "자동 추천 재적용" 버튼이 새로 보임(스크린샷 `screenshot-editor-auto-recommend.jpg`는 적용 후 상태).
2. **자동 추천 — 피스 규칙**: "자동 추천 재적용" 클릭 → 하이햇(HH닫힘) 전부 "R" 라벨, 크래시(CR)도 "R" 표시됨(스크린샷).
3. **자동 추천 — 동시타 스네어→L / 필인 교대**: SN 행을 확대해 확인 — 하이햇과 같은 틱에 겹치는 스네어는 L, 연속 구간은 R/L이 자연스럽게 교대됨, T2(탐2) 행도 L로 표시(스크린샷).
4. **단일 노트 손 지정**: 첫 SN 노트(틱 4, 추천값 "오른손") 선택 → "L" 버튼 클릭 → 정보 바가 즉시 "손: 왼손(지정)"으로 바뀜(aria-label도 "왼손(지정)"으로 동기화 확인).
5. **사용자 지정값이 재분석에도 안 바뀜(REQ-12 핵심)**: 4에서 지정한 노트를 그대로 둔 채 "자동 추천 재적용"을 다시 클릭 → 해당 노트만 "왼손(지정)" 그대로 유지, 나머지는 재계산됨(틱 4070 등 다른 노트는 "추천"으로 정상 갱신)을 확인.
6. **다중선택(Ctrl+클릭)**: 임의의 SN 노트 2개를 각각 클릭·Ctrl+클릭 → "선택: 2개 노트" 바 등장 확인. 일반 클릭(수정키 없음) 2연속은 다중선택이 안 되고 매번 단일 선택으로 "교체"됨을 별도 확인(기존 T2-6 동작 회귀 없음).
7. **RLRL 교대 일괄 적용**: 다중선택 상태에서 "RLRL 교대" 클릭 → 실제로 선택된 두 노트(틱 506, 틱 4070)가 각각 "오른손(지정)"·"왼손(지정)"으로 바뀜(틱순 R→L)을 확인 — 처음엔 엉뚱한 노트(틱 480)를 확인해 "안 바뀐 것처럼" 보였다가, 실제 선택된 노트를 다시 확인해 정상 동작임을 재확인(QA 중 스스로 발견·정정한 착오, 제품 버그 아님).
8. **저장→연습 화면 연동**: "저장" 클릭(204 확인) → 라이브러리 → 곡 제목 클릭(연습 화면) → 상단에 새 "R/L 표시" 체크박스(기본 켜짐) 등장.
9. **레인 R/L 표시(REQ-12 수용기준 핵심)**: 재생 시작 → 스네어 레인 노트 위에 R/L 글자가 실제로 나타남(스크린샷 `screenshot-practice-sticking-on.jpg`), 하이햇 레인 위에도 "R" 표시.
10. **킷 점등 테두리 실선/점선(intent/08-design.md §3)**: 같은 스크린샷에서 SN 킷 서클이 점등되며 **점선(dashed) 테두리**로 표시됨 — 그 순간 활성 노트의 손이 L이었음과 정확히 일치(코드: `isDashedHand` — L/LF만 점선).
11. **R/L 표시 끄기(회귀 없음 확인)**: 체크박스를 끄자 레인 R/L 글자가 즉시 사라지고, 킷 서클도 점선 없이 T2-3 때와 동일한 단순 실선 점등으로 복귀함을 확인(`screenshot-practice-sticking-off.jpg`).
12. **정리**: 재생 정지 → 브라우저 콘솔(`fetch`)로 `GET /songs/2/drumscore` → 전체 노트의 `hand`를 `null`로, `handSource`를 제거한 뒤 `PUT`으로 재저장. 이 단계의 PASS 판정은 서버를 별도로 두 번 더 기동해(새 프로세스, 타임스탬프 붙인 로그) 재검증했다 — `response-body-after-cleanup.json`(실제 `GET` 응답 본문)에서 `grep -c "handSource"` = 0, `hand`가 전부 `null`(비-null `"hand":"..."` 패턴 매치 0건). **이 파일이 실제로 로그에 찍힌 그 요청의 응답인지**까지, 요청 전후 시각(JS `Date`)·응답 본문 SHA-256을 서버의 타임스탬프 로그와 직접 대조해 증명했다(`cleanup-verification-correlation.md` — 브라우저 측 해시 `8dfd070e...`가 커밋된 파일에서 Write 도구가 붙인 개행 1바이트를 뺀 바이트열의 SHA-256과 정확히 일치, 그 요청이 로그의 `2026-10-24T09:04:56.639Z` 한 줄과 37ms 이내로 유일하게 대응). 이 검증 세션의 접근 로그(`server-log-cleanup-verification-2.txt`)에는 `GET`만 있고 `PUT`이 전혀 없어, 검증 자체가 데이터를 추가로 바꾸지 않았다는 것도 로그로 확인된다.
