## 3. 오디오-화면 동기화 실측(의뢰인 첨부 영상 직접 분석) — 실측치 + 가설, 구현 보류
의뢰인이 "Ctrl+Shift+R 후 재생한 걸 녹화했다"며 첨부한 영상(`C:\Users\Jaewoo\Videos\녹음 2026-10-24 211830.mp4`, 35초)을 Python(`opencv-python`, ffmpeg 바이너리는 `imageio-ffmpeg` 패키지로 확보 — 로컬 ffmpeg 미설치)으로 직접 분석:
- 30fps 전체 프레임(1057장)에서 판정선 바로 위 좁은 띠의 "색 픽셀 존재 여부"를 시각 신호로, 같은 구간 오디오(16kHz) RMS 에너지를 오디오 신호로 만들어 교차상관(lag ±667ms 범위)을 계산.
- **전체 구간**: lag=+233ms에서 상관계수 최댓값(0.21, 다른 lag들보다 뚜렷). **노트 밀도가 낮아 신호가 깨끗한 후반부만 떼면 상관계수 0.56(강한 신호)으로 같은 lag(+233ms)에서 피크** — 두 구간 모두 같은 지연값에서 일관되게 나타남.
- **결론(실측)**: 이 녹화에서 화면상 노트가 판정선에 닿는 시점보다 소리가 들리는 시점이 **약 230ms 뒤**였다. 항상 화면이 먼저라는 방향성이 일관됨.
- **한계(과장 금지)**: (1) 화면 녹화 소프트웨어 자체의 AV 버퍼링 차이가 섞여 있을 가능성을 배제 못 함. (2) 상관계수가 1.0에 가깝지 않아(0.21~0.56) "약 230ms"는 추정치이지 정밀 측정값이 아님.
- **원인 가설(코드 검색으로 뒷받침, 미확정)**: `app/web/src` 전체에서 `outputLatency`·`baseLatency` 검색 결과 0건 — `AudioContext.outputLatency`(하드웨어로 실제 소리가 나가기까지의 지연)를 코드 어디서도 읽거나 보정하지 않는다. T2-8에서 스케줄링과 렌더링의 "목표 시각" 계산식이 이미 완전히 동일함을 diff로 확정했으므로, 남은 설명은 "목표 시각"과 "실제로 귀에 들리는 시각" 사이의 간극(outputLatency 미보정) 가능성이 높다고 판단 — 단, 이 세션 브라우저로 확인한 `outputLatency`는 0(이 세션 전용 프리뷰 환경, 의뢰인의 실제 재생 장치 값이 아니라 참고 불가).
- **구현은 이번 라운드에 하지 않음**: "오디오 타이밍·동기"는 위험 작업(`intent/06-pipeline.md` §1-1)이라 설계 변경 전 Codex 모드C가 필요하고, `audioOffsetMs`를 Phase 3까지 0으로 고정한 T2-8의 결정(Q-23)과 상호작용할 여지가 있다. 의뢰인에게 실제 재생 장치의 `outputLatency` 확인 방법을 안내하고 회신을 받은 뒤 Q-24로 등록해 처리할 예정.
