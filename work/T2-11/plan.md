## 조사 결과(구현 전 확인 — 추측 금지, CLAUDE.md §1-1)

### 1. 레인 머리글 위치
`laneRenderer.ts`가 머리글을 캔버스 최상단(y=0~20)에 그리는데, 의뢰인의 실제 시선은 판정선(하단, `hitLineY = height-24`) 근처에 머문다 — 실사용으로 확인된 사실이므로 `intent/04-ui-ux.md` §3 와이어프레임(상단 배치)과 다르더라도 이번 피드백을 그대로 반영한다(의뢰인 본인의 실사용 피드백 = 승인, `intent/` 수정 규칙 충족). 캔버스 하단엔 이미 24px 여백(`height-24` ~ `height`)이 있어 그 안에 20px 머리글 띠를 넣을 수 있음(판정선과 2px 여유).

### 2. 오디오-화면 동기화 실측(영상 분석)
`ffmpeg`(Python `imageio-ffmpeg` 패키지로 확보, 로컬 ffmpeg 미설치)로 영상에서 30fps 프레임 전체(1057장)와 오디오(16kHz mono WAV)를 추출. `opencv-python`으로 판정선 바로 위 좁은 띠(y=554~559px, 전체 폭)에서 "채도 40 초과(배경 검정·판정선 흰색과 구분되는 색상 픽셀)" 존재 여부를 프레임별로 집계해 "시각적 타격 신호" 시계열을 만들고, 같은 프레임 구간의 오디오 RMS 에너지와 교차상관(lag -20~+20프레임)을 계산.
- 전체 구간: lag=+7~8프레임(+233~267ms)에서 상관계수 최댓값(0.19~0.21) — 다른 lag들보다 뚜렷하게 높음.
- 영상 후반부(노트 밀도가 낮아 신호가 깨끗한 구간)만 떼어 같은 분석을 하면 상관계수 0.60(훨씬 강한 신호)으로 같은 lag(+8프레임=+267ms)에서 피크.
- **결론(실측값, 재현 가능)**: 이 녹화에서 "화면상 노트가 판정선에 닿는 시점"보다 "소리가 들리는 시점"이 **약 230~270ms 뒤**다. 항상 화면이 먼저라는 방향성이 일관됨(음수 lag에서 상관계수가 전부 낮거나 음수).
- **원인 가설(코드 검색으로 뒷받침, 미확정)**: `app/web/src/audio/`, `app/web/src/render/` 전체에서 `outputLatency`·`baseLatency` 문자열을 검색한 결과 **0건** — `AudioContext.outputLatency`(하드웨어로 실제 소리가 나가기까지의 지연, Web Audio 표준 스펙)를 코드 어디서도 읽거나 보정하지 않는다. T2-8에서 스케줄링(`scorePlayer.ts`)과 렌더링(`laneRenderer.ts`)의 "목표 시각" 계산식은 이미 완전히 동일함을 diff로 확정했으므로(재확인 완료), 남은 설명은 "목표 시각"과 "실제로 귀에 들리는 시각" 사이의 간극 — 즉 outputLatency 미보정 — 일 가능성이 높다. 다만 (a) 이 세션의 브라우저 도구로 확인한 `outputLatency` 값은 0(이 세션 전용 프리뷰 환경, 의뢰인의 실제 재생 장치가 아님 — 참고 안 됨), (b) 화면 녹화 소프트웨어 자체의 영상/오디오 버퍼링 차이가 섞여 있을 가능성도 배제 못 함 — **확정 원인이 아니라 가설**로 기록.
- **이번 라운드는 구현 보류**: "오디오 타이밍·동기"는 `intent/06-pipeline.md` §1-1의 위험 작업 카테고리라 설계 변경 전 Codex 모드C가 필요하고, `audioOffsetMs`를 Phase 3까지 0으로 고정한 T2-8의 결정(Q-23)과 상호작용할 여지가 있어 섣불리 고치지 않는다. 의뢰인에게 실제 재생 장치에서 `outputLatency` 값을 확인하는 방법을 안내하고 회신을 받아 Q-24로 등록, 다음 라운드(또는 Phase 3)에서 Mode C 설계 검수 후 처리.

### 3. R/L 라벨이 연속 노트에서 안 보이는 버그 — 원인 확정(재현됨)
`laneRenderer.ts`의 노트 그리기 루프는 **레인당 노트 하나 처리할 때마다 "도형 그리기 → 그 바로 위에 R/L 글자 그리기"를 반복**한다(249~267행). `score.notes`는 틱 오름차순이고, 같은 레인에서 틱이 더 늦은(미래) 노트일수록 화면에서는 더 위쪽(작은 y)에 그려진다 — 즉 **나중에 처리되는 노트가 화면상 더 위에 그려지므로, 그 도형이 "직전 노트의 R/L 글자가 그려진 자리"를 그대로 덮어버릴 수 있다**(두 노트 간격이 글자 높이보다 좁으면 100% 겹침). 첨부 영상(frame 30/50, `probe_frame200.png`)에서 실제로 조밀한 SN 구간은 맨 위(가장 늦은 틱) 노트의 라벨만 남고 나머지가 사라진 것으로 확인 — 코드 분석과 영상 증거가 일치.
- **수정**: 레인별 "노트 도형 그리기"와 "R/L 글자 그리기"를 두 단계(2-pass)로 분리 — 한 레인의 노트를 전부 도형으로 그린 뒤, 그 다음에 그 레인의 R/L 글자를 전부 그린다. 이러면 어떤 노트의 도형도 다른 노트의 글자보다 나중에 그려질 수 없어(글자가 항상 마지막 레이어) 겹쳐서 지워지는 일이 없다. 단, 노트 간격이 글자 두 개보다도 좁으면(이 테스트 파일처럼 극단적으로 조밀한 구간) 글자끼리 겹쳐 보일 수 있음 — "사라짐"은 없어지지만 "읽기 어려움"까지는 이번 수정 범위 밖(별도 충돌 회피 로직은 범위 밖, CLAUDE.md §1-6).

### 4. "HH 계속 치면서 SN을 R/L 번갈아 치는 게 물리적으로 가능한가?" — 실제 데이터로 검증
MusicDelta_Grunge(song id=2)의 실제 `drumscore` JSON(API로 조회, 175개 노트)에 `sticking.ts`의 로직을 그대로 재현(Python 이식)해 검증:
- **스네어가 'R'로 배정된 모든 지점(16건)에 대해, 그 시각과 ±60ms 이내에 하이햇/라이드 타격이 있는지 확인 → 0건.** 즉 필인 교대가 'R'을 배정하는 순간은 전부 하이햇이 "쉬는" 타이밍에 떨어져 있었다 — 이 곡에 한해서는 "HH 계속 치면서 SN도 R로 동시에 친다"는 충돌이 실제로 발생하지 않음(가정이 아니라 전수 확인).
- **그런데 다른 종류의 진짜 충돌을 발견**: 'R'로 고정 배정되는 피스들(`hihat_closed`/`hihat_open`/`ride`/`crash`, `STICKING_PIECE_RULES`) 중 **크래시와 하이햇이 정확히 같은 틱(tick=4550)에서 둘 다 'R'로 배정**된 사례가 실제로 있었다(0ms 간격 — 한 손이 같은 순간 두 악기를 칠 수 없음, 물리적으로 불가능). 기존 "동시 타격 회피" 로직(81~88행)은 **스네어와 하이햇/라이드의 동시 틱만** 처리하고, 크래시는 전혀 검사 대상이 아니었던 것이 원인 — 설계 공백(버그).
- **수정**: 동시 타격 회피 로직을 "스네어 전용"에서 "고정 R 배정 피스들끼리의 동시 틱"으로 일반화. 우선순위 `hihat_closed > hihat_open > ride > crash`(하이햇/라이드는 통상 타임키핑을 담당해 손을 유지, 크래시는 악센트라 손을 비켜주는 쪽이 더 자연스럽다고 판단 — 전문 검증 안 된 휴리스틱이라 Q-11에 추가 등록 예정) — 더 낮은 우선순위 피스가 더 높은 우선순위 피스와 같은 틱이면 'L'로 보낸다.
- 의뢰인 질문에 대한 답: 질문하신 "HH 연속 + SN 교대" 패턴 자체는 (적어도 이 곡에서는) 충돌이 없는 정상 패턴으로 확인됐지만, 질문을 계기로 조사하다가 **크래시-하이햇 동시타격이라는 진짜 다른 버그**를 찾아 같이 고친다.
