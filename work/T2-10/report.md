## 구현 근거 (실행 결과로 확인)
- **레인 머리글은 추측이 아니라 명세 문서+전수 코드 검사로 확인한 실제 누락**: `intent/04-ui-ux.md` §3 와이어프레임에 "HH CR SN T1 T2 FT RD KK ← 레인 머리글"이 명시돼 있고, `08-design.md` §4 타이포그래피 표에도 전용 행("레인 머리글 18px 700")이 있었다 — 즉 처음부터 계획에 있던 요구사항이었다. 처음엔 `lane.label` 같은 특정 변수명 패턴만 `grep`했는데, Codex가 "다른 이름으로 그렸을 가능성까지 배제 못 한다"고 지적 — Canvas 2D에서 텍스트를 그리는 `ctx.fillText` 호출 전부를 센 결과 수정 전(main) 283줄 전체에서 **정확히 1건**(스티킹 R/L 글자)뿐이었음을 확인했으나, Codex가 다시 "`fillText`가 유일한 API라는 전제가 틀렸다(Canvas 2D엔 `strokeText`도 있음)"고 지적 — `fillText`와 `strokeText`를 함께 검색하도록 교체한 결과 `strokeText`는 main·수정 후 모두 0건, `fillText` 건수는 그대로(main 1건, 수정 후 2건)임을 확인해 Canvas 2D의 텍스트 그리기 API 둘 다로 전수 배제를 완성(`qa-evidence/T2-10/raw_log.txt`). "스크롤 중에도 항상 보인다"는 주장은 "머리글 그리기가 매 프레임 조건 없이 실행된다"(코드로 확정)와 "실제로 매 순간 화면에 보인다"(미증명, 한 시점 스크린샷으로만 확인)를 구분해 표현(Codex 모드B 지적 반영).
- **R/L 투명도는 의도적으로 안 건드림**: `08-design.md` §1 "원칙(의뢰인 결정, 2026-10-23)"에 속한 §3 "자동 추천 값은 50% 투명도"는 이미 승인된 구체적 수치라, "잘 안 보인다"는 피드백에도 폰트 크기만 키우고 투명도는 그대로 뒀다 — 투명도까지 바꾸려면 별도 확인이 필요하다고 판단(CLAUDE.md §1-6 범위 밖 작업 금지).

## 사용자에게 전달할 내용 — 질문·요청사항 답변
- **"SN을 빠르게 R/L 번갈아 치는 게 맞아?"**: `score/sticking.ts`의 설계 그대로입니다 — 스네어/탐이 **간격 좁게(16분음표 이내) 연속**되면 "필인"으로 보고 R/L을 교대시키고, 간격이 넓어 필인으로 안 묶이면 전부 기본손(R)으로 표시합니다. 실제 화면에서 "R R R R"처럼 연속된 걸 보셨다면 그 구간은 간격이 넓어 "필인"으로 안 묶인 것 — 음악적으로 맞는지는 여전히 전문 검증 안 된 휴리스틱이라 확답은 못 드립니다(Q-11).
- **오디오-화면 잔여 간격**: T2-8에서 이미 코드 두 곳(소리 스케줄링/화면 렌더링)이 완전히 같은 계산식을 쓰도록 맞췄습니다(diff로 확정 가능한 사실). 그런데도 여전히 소리가 늦게 들린다면, 추가로 의심되는 건 (a) 브라우저가 아직 예전 코드를 쓰고 있거나(이전에 안내드린 전체 새로고침), (b) 실제 오디오 출력 장치의 하드웨어 지연(특히 블루투스 이어폰·스피커는 수십~수백 ms 지연이 흔함, 소프트웨어로 쉽게 없앨 수 없는 물리적 지연)입니다. 어떤 장치로 소리를 듣고 계신지 확인 부탁드립니다.
