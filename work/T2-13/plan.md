# T2-13 계획 — Phase 2 게이트 6차 피드백(2026-10-24)

## 피드백 원문 요약
1. "희미한 선 3줄+진한 선 1줄이 쌍으로 반복되는데 한 줄이 1박씩 쳐서 4/4박자처럼 나오는거야? ab루프 돌려보니 4개 선이 1마디가 맞는거 같은데(추측)"
2. "왜 한 마디에서 같은 리듬이 반복되면 보통 같은 박자에 들어갈텐데 노트의 위치들이 조금씩 마디마다 다를까?"
3. "hh의 R부분은 잘 안보여서 위치를 변경하던가 색을 변경하던가 해야할 거 같아."

## 조사 결과(구현 전 확인)

### 1. 마디/박선 — 의뢰인 추측이 정확함(코드로 확인)
`render/layout.ts`의 `barBeatLines()`: `clicksPerBar = Math.round(beatsPerBar(timeSignature, 4))`. 4/4 박자는 `beatsPerBar(4,4) = 4`이므로 **박마다(4번째 클릭마다) 마디선(굵게), 그 외엔 박선(얇게)**을 그린다 — "희미한 선 3줄+진한 선 1줄=1마디"는 코드와 정확히 일치. 버그 아님, 추측이 맞았음을 확인.

### 2. 스네어 백비트가 마디마다 밀리는 이유 — 원본 데이터 자체의 패턴(앱 버그 아님)
실제 곡 데이터(song id=2) 스네어 46개 틱을 마디별로 묶어 분석:
- 끊기지 않은 구간(예: 9~13마디)에서 "마디 안 둘째 스네어 박"의 위치가 **마디마다 약 0.36박(약 179ms)씩 꾸준히 밀린다**(단순 잡음이 아니라 선형적으로 증가) — 8·14마디 같은 "필인/전환" 마디에서 리셋되고 다시 비슷한 비율로 밀리는 패턴 반복.
- **원인 후보를 좁히기 위해 원본 MIDI 파일(`data/songs/2/original.mid`)을 우리 앱의 import 경로와 똑같은 라이브러리(`@tonejs/midi`)로 직접 파싱**해 확인: 템포 이벤트가 **정확히 1개**(120bpm, 틱 0)뿐이었다 — 우리 import 코드(`midiEvents.ts`)가 "첫 템포만 읽고 나머지를 버린다"는 가설은 틀렸다(버릴 "나머지"가 애초에 없음). 즉 이 드리프트는 **원본 MIDI 파일의 틱 값 자체에 이미 들어있는 패턴**이지, 우리 앱이 재생·렌더링하면서 만들어내는 버그가 아니다.
- **남은 설명(둘 다 가능, 확정 못 함)**: (a) 이 곡은 실제 사람이 연주한 라이브 녹음의 채보라 연주자의 자연스러운 템포 변동(특정 구간에서 조금씩 빨라지다 필인에서 리셋 — 록/그런지 장르에서 흔함)이 그대로 반영됐을 가능성, (b) ADTOF 자동 채보 모델의 박자 추적(onset detection)이 특정 구간에서 체계적으로 조금씩 어긋났을 가능성(T2-9에서 이미 확인한 이 파일의 낮은 정확도와 같은 맥락). 어느 쪽이든 **우리 앱의 코드 버그는 아님**(원본 데이터의 성질) — 확정은 Phase 3에서 원본 오디오와 직접 비교해야 가능.
- **구조적 시사점**: `DrumScore.meta.bpm`은 고정값 하나뿐(템포 맵 없음) — 실제 라이브 연주처럼 템포가 미세하게 변하는 곡은 이 형식으로 "정확히" 표현할 수 없다. Phase 3에서 사용자 음원을 자동 채보하게 되면 같은 현상(노트가 마디마다 살짝 밀려 보임)이 재발할 수 있어 신규 open question으로 등록.

### 3. HH R 라벨 가독성
HH 레인은 거의 매 서브디비전마다 노트가 연속으로 떨어져(continuous hi-hat pattern), 레이블 주변에 다음 노트의 X자 획이 시각적으로 겹쳐 글자가 묻혀 보인다 — 투명도·색 자체의 대비 문제라기보다 "배경이 바쁜(busy) 상태"에서 생기는 가독성 문제.
- **수정**: 글자 색/투명도는 그대로 두고(투명도는 의뢰인 결정 수치), 글자를 그리기 전에 캔버스 배경색으로 얇은 테두리(halo)를 먼저 그려 어떤 배경 위에서도 글자 윤곽이 도드라지게 함 — 표준 가독성 기법(스트로크 먼저, 채우기 나중).
