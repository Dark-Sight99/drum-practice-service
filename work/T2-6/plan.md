# T2-6 계획

## 목표
`intent/05-todo.md` T2-6: "편집기(추가/삭제/이동, 실행 취소) (REQ-03)".

## 근거
REQ-03: 노트 추가/삭제/이동(시간축 격자 스냅: 4·8·16분, 셋잇단), 킷 피스 변경, 셈여림(약/중/강 3단계), 실행취소/다시실행(20단계 이상), BPM·박자표 수정(곡 전체 1개 값). 수용 기준: **"편집 → 저장 → 재로드 시 동일"** — T2-5가 만든 영속화 경로(서버에 실제 저장)가 있어야 의미 있게 검증 가능.

`intent/04-ui-ux.md` §2: "편집: 피아노롤 형태의 드럼 그리드(세로 = 킷 피스, 가로 = 시간), 악보 인식 결과 확인용으로 원본 사진을 옆에 표시".

## 범위 — 다룸 / 안 다룸
**다룸**
- 편집 화면: 피아노롤 그리드(세로 9개 킷 피스 행, 가로 시간축).
- 노트 추가(빈 칸 클릭), 삭제(선택 후 Delete), 이동(선택 후 방향키 — 격자 스냅).
- 킷 피스 변경(선택 후 위/아래 방향키로 행 이동).
- 셈여림 3단계(선택 후 버튼으로 약/중/강 지정).
- 격자 단위 선택(4분/8분/16분/셋잇단).
- 실행취소/다시실행(Ctrl+Z/Ctrl+Y 또는 버튼, 스냅샷 기반, 20단계 이상 — 상한을 인위적으로 20에 맞추지 않고 넉넉히 둠).
- BPM·박자표 수정(곡 전체 1개 값 — 입력 필드).
- 저장: `PUT /songs/{id}/drumscore` 신규 엔드포인트로 서버에 영속화(DRUMSCORE_EDITED 자산). 라이브러리에서 편집 화면 진입점("편집" 버튼) 추가.

**안 다룸**
- "악보 인식 결과 확인용 원본 사진 옆 표시" — OMR(종이 악보, 경로 B) 전용 UI 요소. Phase 2는 디지털 악보만 다뤄 원본 사진 자체가 없음(Phase 4에서 추가).
- 마우스 드래그로 노트 이동 — 방향키 이동으로 "이동" 요구사항을 충족(REQ-03은 구체적 조작 방식을 지정하지 않음), 드래그앤드롭은 구현 복잡도 대비 가치가 낮다고 판단(가정, 아래 §가정 참고). 추후 필요하면 드래그 추가.
- 중간 변속(마디별 BPM) — REQ-03이 "[확장]"으로 명시.
- 스티킹(hand 필드) 편집 UI — T2-7 범위.
- 다중 사용자 동시 편집·충돌 해결 — 이 서비스는 곡 라이브러리가 사용자별로 완전히 분리(REQ-08)라 같은 곡을 동시에 편집할 상황 자체가 없음(가정).

## 설계

### 1. 백엔드 — `PUT /songs/{id}/drumscore`(신규, `app/server/api/songs.py`)
- 입력: JSON body — `api/schemas.py`의 `DrumScoreIn`으로 구조+수치 불변식 검증(T2-5와 동일 모델 재사용, 업로드와 저장이 같은 신뢰 경계를 가져야 함).
- 소유자 검사: 기존 `get_owned_song` 의존성 재사용(T2-5 Codex 모드C C-006 패턴 그대로).
- 저장: 해당 곡의 `Asset(kind=DRUMSCORE_EDITED)`이 이미 있으면 **파일 내용만 덮어쓰고 행은 유지**(업데이트), 없으면 새로 생성. **DB에 (song_id, kind) 유니크 제약을 추가하지 않는다** — `AssetKind`에는 `SHEET_IMAGE`처럼 한 곡에 여러 장이 정당하게 있을 수 있는 종류가 섞여 있어, 모든 종류에 일괄 유니크 제약을 걸면 Phase 4(OMR 다중 페이지)와 충돌한다(가정). 대신 애플리케이션 코드에서 "같은 song_id+kind의 기존 행을 찾아 덮어쓰기"로 중복 생성을 막는다 — 동시 편집 시나리오가 없다는 가정(§범위)과 맞물려 이 정도면 충분하다고 판단, Codex 모드C에서 다르게 보면 반영.
- 파일 저장은 T2-5의 `file_storage.write_song_file(song_id, "drumscore_edited.json", content)` 그대로 재사용(고정 파일명, 경로조작 재검증 이미 적용됨).
- 응답: `SongOut`(200) 또는 204 — 기존 `GET /songs/{id}/drumscore`가 `DRUMSCORE_EDITED`를 우선하도록 이미 T2-5에서 설계돼 있어, 저장 직후 재조회하면 바로 편집본이 반환됨(수용 기준 "저장 → 재로드 시 동일"의 서버 쪽 근거).

### 2. 프론트엔드 — 순수 로직(단위 테스트 가능)
`app/web/src/features/editor/grid.ts`:
- `GridUnit = '4n' | '8n' | '16n' | '8nt'`(8분음표 셋잇단).
- `ticksPerGridUnit(unit, ppq)`: `ppq / {4n:1, 8n:2, 16n:4, '8nt':3}[unit]`.
- `snapTick(tick, unit, ppq)`: 가장 가까운 격자선으로 반올림.
- `EDITOR_ROWS`: 9개 킷 피스 행 순서(연습 화면 8레인과 달리 하이햇 열림/닫힘을 **별도 행**으로 — 에디터는 정확한 피스 지정이 필요해서, T2-3 `LANES`와 다른 목적의 별도 상수, 가정).

`app/web/src/features/editor/editHistory.ts`:
- 스냅샷 기반 실행취소 스택: `pushHistory(state, snapshot)`, `undo(state)`, `redo(state)` 순수 함수. 상한 없음(REQ-03 "20단계 이상"을 넉넉히 만족).

`app/web/src/features/editor/velocity.ts`:
- `VELOCITY_TIERS = { soft: 40, mid: 90, strong: 120 }`(MIDI 0~127 범위 안에서 임의 설정 — 명시된 기준 없어 가정, §가정 참고). `velocityTierOf(velocity)`: 가장 가까운 티어 판별(기존 노트의 현재 티어를 UI에 표시하는 용도).

### 3. 프론트엔드 — 화면
`features/editor/EditorScreen.tsx`:
- DOM/SVG 기반 그리드(Canvas 아님 — T2-3 레인 렌더러와 달리 매 프레임 애니메이션이 필요 없는 정적·상호작용 화면이라, 클릭/키보드 이벤트를 자연스럽게 받을 수 있는 DOM 쪽이 Canvas 수동 히트테스트보다 간단하다고 판단, 가정).
- 상단 바: BPM·박자표 입력, 격자 단위 선택, 실행취소/다시실행 버튼, 저장 버튼.
- 그리드: 9행(킷 피스) × 가로 스크롤 가능한 시간축. 빈 칸 클릭 → 노트 추가(현재 격자 단위로 스냅, 기본 셈여림 "중"). 노트 클릭 → 선택(강조 표시) → 방향키(←→ 시간 이동, ↑↓ 피스 변경)·Delete(삭제)·숫자 1/2/3 또는 버튼(셈여림 변경).
- 모든 편집 동작마다 `editHistory`에 스냅샷 push.
- 저장 버튼 → `validateDrumScore()`(T1-5, 클라이언트 쪽 1차 확인) → `saveSongDrumScore(id, score)`(신규 API 함수, `PUT`) → 성공 시 라이브러리로 복귀(또는 저장됨 표시).

`LibraryScreen.tsx`: 곡 카드에 "편집" 버튼 추가(기존 "이름변경"·"삭제" 옆) — 클릭 시 `fetchSongDrumScore()`로 현재 DrumScore(편집본 있으면 그것)를 가져와 편집 화면으로 이동.

`App.tsx`: `screen` 상태에 `'editor'` 추가.

## 테스트 계획
**프론트 단위 테스트(vitest)**
1. `ticksPerGridUnit`/`snapTick`: 4종 격자 단위 각각에서 올바른 틱 값, 경계값(정확히 격자선 위의 틱) 스냅 확인.
2. `editHistory`: push 후 undo로 직전 상태 복원, redo로 다시 앞으로, 20회 이상 연속 push해도 전부 undo 가능.
3. `velocityTierOf`: 3개 티어 경계값 판별.
4. `EditorScreen` 컴포넌트(React Testing Library, jsdom — **Canvas·Tone.js가 아니라 순수 DOM 이벤트라 jsdom에서 실제로 테스트 가능**, T2-3·T2-4·T2-5와 다른 지점): 빈 칸 클릭 → 노트 추가됨, 노트 클릭 후 Delete → 삭제됨, 방향키로 이동, undo/redo 버튼 동작, 저장 버튼 클릭 시 `saveSongDrumScore` 호출 인자 확인(fetch 모킹).

**백엔드(pytest)**
5. `PUT /songs/{id}/drumscore` 정상 저장 → 같은 song_id로 `GET .../drumscore` 재조회 시 저장한 내용과 동일(REQ-03 수용 기준의 서버 쪽 핵심 검증).
6. 두 번 연속 저장 — `Asset` 테이블에 `DRUMSCORE_EDITED` 행이 1개만 유지되는지(덮어쓰기 확인, 중복 생성 안 됨).
7. 비로그인 401, 타 사용자 403 아닌 404.
8. T2-5와 같은 수치 불변식 위반 케이스(최소 대표 2~3개) 거부 확인 — 같은 `DrumScoreIn` 재사용이므로 전체 재검증은 안 하고 "같은 모델을 쓴다"는 것만 확인.

**수동 QA(실제 브라우저 + 실제 서버)**
9. 노트 추가·삭제·이동·킷 변경·셈여림 변경을 실제로 마우스+키보드로 조작.
10. BPM·박자표 수정 후 저장.
11. **REQ-03 수용 기준 직접 검증**: 편집 → 저장 → 페이지 새로고침(또는 새 탭) → 편집 화면 다시 열기 → 편집한 내용이 그대로 보이는지.
12. 편집한 곡을 연습 화면에서 재생 — 편집본이 재생되는지(T2-5가 이미 `GET .../drumscore`를 DRUMSCORE_EDITED 우선으로 설계해둠 — 실제로 연결되는지 처음 확인).
13. 실행취소 20회 이상 연속 수행 — 전부 되돌아가는지.

## 가정
- 셈여림 3단계의 구체 velocity 값(약=40, 중=90, 강=120)은 명시된 기준이 없어 임의 설정(MIDI 0~127 범위 안, `08-design.md`의 "60%/85%/100%" 밝기 비율과는 별개 — 그건 렌더링 표현, 이건 저장되는 실제 값).
- 노트 이동은 방향키 기반(격자 스냅), 마우스 드래그는 범위 밖 — 추후 필요시 추가.
- 에디터 9행은 하이햇 닫힘/열림을 별도 행으로 구분(연습 화면 8레인과 다른 상수) — 정확한 피스 지정이 편집기의 핵심 기능이라 필요.
- `Asset(song_id, kind)` 유니크 제약은 DB에 추가하지 않고 애플리케이션 코드로 중복 방지(다른 AssetKind와의 충돌 방지).
- 동시 편집(여러 세션이 같은 곡을 동시에 편집)은 고려 안 함 — REQ-08상 곡이 사용자별로 완전히 분리돼 일어나기 어려운 상황.
- "악보 인식 결과 확인용 원본 사진" UI는 Phase 4(OMR)로 연기.
