## 설계

### 1. 백엔드 — `PUT /songs/{id}/drumscore`(신규, `app/server/api/songs.py`)
- 입력: JSON body — `api/schemas.py`의 `DrumScoreIn`으로 구조+수치 불변식 검증(T2-5와 동일 모델 재사용, 업로드와 저장이 같은 신뢰 경계를 가져야 함). BPM 등 값의 범위는 업로드 때와 동일한 `DrumScoreIn` 제약을 그대로 따름(최소값을 따로 더 좁히지 않음 — 편집기 입력 필드도 이 범위(유한한 양수)만 맞추면 되므로 프론트·백엔드 간 불일치 없음, Codex 모드C C-005 반영).
- 소유자 검사: 기존 `get_owned_song` 의존성 재사용(T2-5 Codex 모드C C-006 패턴 그대로).
- **중복 방지(Codex 모드C C-001 반영 — "찾아서 덮어쓰기"만으론 동시 요청 경쟁 상태를 못 막는다는 지적)**: DB 레벨에서 막는다 — `Asset`에 **`DRUMSCORE_EDITED` 종류에만 적용되는 부분 유니크 인덱스**(SQLite `CREATE UNIQUE INDEX ... WHERE kind='drumscore_edited'`, SQLAlchemy `Index(..., unique=True, sqlite_where=text(...))`로 구현 가능함을 실제 실행으로 확인 — 같은 song_id+`drumscore_edited` 두 번째 삽입 시 `IntegrityError` 발생 확인)을 Alembic 마이그레이션으로 추가. **모든 `AssetKind`에 일괄 유니크 제약을 걸지 않는 이유**: `SHEET_IMAGE`처럼 한 곡에 여러 장이 정당하게 있을 수 있는 종류가 섞여 있어(Phase 4 OMR 다중 페이지), 전역 유니크 제약은 그런 종류와 충돌한다 — `DRUMSCORE_EDITED`에 **한정된** 부분 인덱스이므로 문제없음(Codex 모드C C-006 반영, 범위 명확화). 애플리케이션 코드는 기존 행을 찾아 UPDATE 시도 → 없으면 INSERT하되, INSERT가 `IntegrityError`(동시 요청으로 그 사이 다른 요청이 먼저 만든 경우)면 다시 조회해 UPDATE로 재시도(낙관적 upsert 패턴).
- **파일 쓰기 원자성(Codex 모드C C-002 반영)**: `file_storage.write_song_file()`을 임시 파일에 먼저 쓴 뒤 `Path.replace()`(같은 볼륨 내 원자적 교체 — Python 공식 문서: POSIX `rename()`/Windows `MoveFileEx`로 원자적)로 최종 파일명으로 바꾸도록 수정. 이 함수는 T2-5의 업로드 경로도 같이 쓰므로, 쓰기 도중 실패해도 기존 파일(또는 아무 파일도 없음)이 그대로 남고 "반쯤 쓰인 파일"이 생기지 않게 되는 효과가 업로드에도 적용됨(공유 primitive를 더 안전하게 만드는 것 — 범위 확대 아님).
- 저장은 DB 커밋 성공 후에만 "성공"으로 응답 — DB 커밋이 실패하면 새로 쓴 파일(이미 원자적으로 교체됐을 수 있음)이 DB의 `file_path`가 가리키는 내용과 다를 위험은 남지만(완전한 2단계 커밋은 과한 설계로 판단), 적어도 파일 자체가 손상되는 경우는 원자적 교체로 막는다 — 가정.
- **응답 계약 명확화(Codex 모드C C-007 반영)**: `204 No Content`로 고정(기존 `DELETE /songs/{id}`와 같은 관례 — 프론트는 이미 저장할 DrumScore를 들고 있어 본문을 돌려받을 필요가 없음). 저장 성공 직후 `GET /songs/{id}/drumscore`를 다시 부르면 `DRUMSCORE_EDITED`가 우선 조회되므로(T2-5에서 이미 구현·테스트됨 — `api/songs.py`의 `get_song_drumscore()` 실제 코드로 재확인) 방금 저장한 내용이 그대로 돌아온다.
- **동시 편집 충돌 처리(Codex 모드C C-008 반영, 리스크로 기록)**: 충돌 감지 없음 — 나중에 저장한 쪽이 이긴다(last-write-wins). 이 서비스는 곡이 사용자별로 완전히 분리되고(REQ-08) 동시 편집 UI가 없어 실제로 같은 곡을 두 세션이 동시에 저장할 상황은 드물다고 보지만, 발생하면 데이터 손실 가능성이 있음을 알고 넘어간다(명시적 리스크 인수).

## 가정
- 셈여림 3단계의 구체 velocity 값(약=40, 중=90, 강=120)은 명시된 기준이 없어 임의 설정(MIDI 0~127 범위 안, `08-design.md`의 "60%/85%/100%" 밝기 비율과는 별개 — 그건 렌더링 표현, 이건 저장되는 실제 값).
- 노트 이동은 방향키 기반(격자 스냅), 마우스 드래그는 범위 밖 — 추후 필요시 추가.
- 에디터 9행은 하이햇 닫힘/열림을 별도 행으로 구분(연습 화면 8레인과 다른 상수) — 정확한 피스 지정이 편집기의 핵심 기능이라 필요.
- 실행취소 스택 상한은 100단계(REQ-03 "20단계 이상" 충족 + 메모리 보호, Codex 모드C C-003).
- 동시 편집 충돌 감지는 없음(last-write-wins) — 동시 편집 시나리오가 드물다는 가정과 함께 받아들이는 리스크(Codex 모드C C-008).
- 서버 저장은 "파일 원자적 교체"까지만 보장하고 파일·DB 간 완전한 2단계 커밋은 하지 않음(과한 설계로 판단) — DB 커밋 실패 시 파일은 이미 갱신됐는데 DB의 file_path 내용과 실제 파일 내용이 아주 짧은 순간 불일치할 이론적 가능성은 남음(가정, 실질적 위험은 낮다고 판단).
- `Asset(song_id, kind)` 유니크 제약은 DB에 추가하지 않고 애플리케이션 코드로 중복 방지(다른 AssetKind와의 충돌 방지).
- 동시 편집(여러 세션이 같은 곡을 동시에 편집)은 고려 안 함 — REQ-08상 곡이 사용자별로 완전히 분리돼 일어나기 어려운 상황.
- "악보 인식 결과 확인용 원본 사진" UI는 Phase 4(OMR)로 연기.
