> 한 줄 요약: pretender.mp4 한 곡으로 (A)음량만 더 올림 (B)6갈래 분리 (C)둘 다, 3가지를 비교해 하이햇(GM42) 검출이 늘어나는지 실측하는 1회성 실험 — 운영 코드는 건드리지 않음.

# T3-45 — 하이햇 검출 개선 레버 실험 계획

## 배경
- Q-42(`intent/07-open-questions.md`): GM42(하이햇) 채널이 pretender 곡에서 0건 검출.
- 의뢰인 질문 2가지:
  1. 6갈래(kick/snare/tom/hihat/ride/crash)를 다 가져오면 더 정확해지지 않을까?
  2. 하이햇이 거의 안 잡히는 게 "소리가 작아서"일 수도 있나?
- 의뢰인 지시: 코드(운영 파이프라인) 수정 금지, pretender.mp4 1곡으로 3가지 변형만 비교 실험.

## 이미 알고 있는 사실(추측 아님, 코드로 확인)
- `modules/transcriber/adtof_transcriber.py`의 `normalize_loudness()`가 이미 드럼 스템
  RMS를 -18dBFS로 정규화한 뒤 ADTOF에 넘기고 있음(T3-2 피드백 2차에서 "backnumber" 곡으로
  실측 확인된 기존 레버). 즉 "음량을 올린다"는 건 **이 -18dBFS보다 더 큰 목표치로
  재정규화**하는 실험이 됨(완전히 새로운 레버가 아니라 기존 레버의 세기를 더 키우는 것).
- 6갈래 분리 모델(DrumSep, MDX23C aufr33-jarredou)은 이 프로젝트에 아직 없음 —
  라이선스가 출처마다 다르게 표시됨(CC BY-NC-ND / CC BY-NC-SA / 명시 없음, 2026-10-28
  웹 조사) → 다운로드 전 의뢰인 승인 필요(파일 다운로드 규칙) + 채택 시
  `intent/03-architecture-stack.md` 라이선스 표 기록 필요(CLAUDE.md §6).

## 실험 설계
모두 같은 원본(pretender.mp4) → 같은 Demucs 분리 결과(`stem_drums.wav`)에서 시작.

| 변형 | 내용 | 상태 |
|---|---|---|
| 기준(현재 운영값) | `normalize_loudness` 목표 -18dBFS 그대로 → ADTOF | 실행 |
| A. 음량만 ↑ | 목표 RMS를 더 높여(-18→-8dBFS 등 여러 값) → ADTOF | 실행 |
| B. 6갈래 분리만 | DrumSep으로 하이햇 등 6스템 분리 → 각 스템 ADTOF/온셋 검출 | **다운로드 승인 대기** |
| C. 음량↑ + 6갈래 | B의 하이햇 스템에 추가로 게인↑ | **다운로드 승인 대기** |

## 검증 방법(T3-44와 동일 원칙 — 건수만 보지 않음)
1. GM42(하이햇) 매핑 노트 건수.
2. 스펙트럼 특징(중심주파수, <300Hz 저주파 비율) — 진짜 하이햇다운 소리인지,
   아니면 그냥 노이즈/다른 악기를 잘못 하이햇으로 잡은 것인지 구분.
3. (가능하면) 독립 onset 검출과 겹치는지.

## 범위
- `app/server/modules/*` 운영 코드는 이번 실험에서 전혀 수정하지 않음 — 이 폴더의
  1회성 스크립트에서 기존 함수를 그대로 import해서 호출만 함.
- 결과가 유의미하면, 반영 여부는 별도 작업(Phase 승인)으로 논의.
