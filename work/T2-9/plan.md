# T2-9 계획 — Phase 2 게이트 2차 피드백

## 배경
T2-8 수정 후에도 의뢰인이 "노트 하단이 판정선 닿을 때가 아니라 상단이 다 지나고 나서 소리가 들린다"고 재보고, 추가로 "초반 노트가 실제 음과 전혀 다르고 중간에 소리가 사라진다"며 MusicDelta_Grunge의 출처를 질문.

## 조사 1 — 판정 순간 정밀도
`laneRenderer.ts`는 `noteYPosition()`으로 노트 도형의 **중심**이 판정선에 오는 시각을 계산해 그 좌표에 도형을 그린다. 도형 높이(`noteSize`, 16~28px)가 있어 시각적으로는: 하단 모서리가 중심보다 먼저 판정선에 닿고, 상단 모서리는 중심보다 늦게 판정선을 지난다. REQ-06·리듬게임 관례상 "닿는 순간"은 하단 모서리 기준이 맞다 — 중심 기준은 그 절반만큼(noteSize/2 픽셀, 현재 속도에서 수십 ms 수준) 어긋나 있었다.

**위험 작업 여부**: 이 수정은 노트의 **시각(초)** 계산 자체(`noteTimeOf`, `noteYPosition`의 입력)를 전혀 안 건드리고, 이미 계산된 Y좌표를 그리는 위치만 `noteSize/2`만큼 고정 이동한다 — 오디오 스케줄링·판정창(`hitWindowSeconds`) 계산과 무관. `intent/06-pipeline.md` §1-1의 "오디오 타이밍·동기"(시각 계산 자체를 바꾸는 작업)에 해당하지 않는다고 판단 — Codex 모드C 생략, T2-7의 표시 전용 변경과 같은 패턴.

## 조사 2 — MusicDelta_Grunge 출처 확인(바이트 비교로 확정)
`data/songs/2/original.mid`와 `data/t0-2-work/MusicDelta_Grunge.mid`(T0-2 ADTOF 평가 파이프라인 산출물)를 `diff <(xxd ...) <(xxd ...)`로 비교 — **바이트 단위로 완전히 동일**함을 확인. 즉 지금 "MusicDelta_Grunge"로 업로드된 곡은 사람이 만든 정답 MIDI가 아니라, **Phase 0에서 ADTOF 모델이 실제 드럼 음원(`MusicDelta_Grunge_Drum.wav`, MDB Drums 데이터셋)을 듣고 자동으로 받아쓴 결과물**이다. `qa-evidence/T0-2/result_raw.json`에 이미 이 트랙의 분류별 F-measure가 기록돼 있음: 킥 0.97, 스네어 0.85, **탐 0.33**(재현율 0.25 — 실제 탐 히트의 75%가 아예 빠져 있음). "초반 노트가 실제 음과 다름", "중간에 소리가 사라짐"은 이 수치와 정확히 들어맞는 **AI 채보 모델의 기존에 이미 측정된 한계**이지, T2-x 구현의 새 버그가 아니다.

## 설계
### 코드 변경
- `render/laneRenderer.ts`: 노트 도형을 `yCenter - noteSize/2`에 그리도록 수정(하단 모서리가 판정선과 일치).

### 문서·소통(코드 변경 없음)
- 의뢰인에게 MusicDelta_Grunge의 실제 출처(ADTOF 자동 채보 테스트 데이터)와 정확도 한계를 설명하고, 정확한 노트 비교가 목적이면 사람이 직접 만든 MIDI나 `drum_test_roundtrip.gp` 같은 클린 샘플을 권장.
- 하드 리프레시 안내: 이전 피드백 재현 시 브라우저 탭이 오래 열려있었다면 Vite HMR이 최신 코드를 완전히 반영 못 했을 수 있음(이 세션 자체 QA 중에도 같은 현상을 겪어 전체 새로고침으로 해결한 전례가 있음, `qa-evidence/T2-8/codex-modeA.md` 참고).
