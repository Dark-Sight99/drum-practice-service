# 06. 멀티 에이전트 파이프라인

## 1. 역할
| 역할 | 실행 주체 | 권한 | 책임 |
|---|---|---|---|
| 마스터 AI | Claude Code 메인 세션 | 전체 | 기획(사용자 대화 포함), 작업 분해, 토론 소집, 배정, 병합, 1차 검수, 최종 승인 |
| 리서처 | Claude 서브에이전트 | 읽기 전용 + `work/<ID>/research-*.md` 쓰기 | 라이선스·데이터셋·문서 조사. 사실과 출처만 보고 |

| 서버·오디오 개발 | Claude 서브에이전트 | app/server 쓰기 | 구현 + 단위 테스트 |
| QA 담당 | Claude 서브에이전트 | 테스트 실행, qa-evidence 쓰기 | 시뮬레이션·E2E·캡처 |

| 전략 실장 (검수) | **Codex CLI, 읽기 전용** | 코드 수정 불가 | 코드 리뷰, 리스크·전략 보완점, APPROVE/REQUEST_CHANGES |

역할별 상세 정의(읽을 것·쓸 수 있는 곳·금지·보고 형식, 작업 지시서·보고서 양식)는 `09-agent-roles.md`. 기획 담당은 별도 에이전트 없이 마스터가 맡는다(의뢰인 결정).

### Codex 연동 초기 세팅 (사람이 1회 수행)
1. Codex CLI 설치·로그인: `npm install -g @openai/codex` → `codex login` (ChatGPT 구독 또는 OpenAI API 키 필요, 사용량은 Codex 한도에서 차감)
2. Claude Code에 OpenAI 공식 플러그인 설치(Claude Code 입력창에서):
   ```
   /plugin marketplace add openai/codex-plugin-cc
   /plugin install codex@openai-codex
   /reload-plugins
   /codex:setup
   ```
3. 리뷰 게이트(`/codex:setup --enable-review-gate`)는 **켜지 않는다** — Claude가 멈출 때마다 자동 리뷰가 돌아 사용량을 빠르게 소모할 수 있음(플러그인 README 경고). 필요해지면 사용자가 지켜볼 때만 켠다.
4. Claude가 매번 허락을 묻지 않도록 `.claude/settings.json`에 Codex 검수 명령만 허용(마스터가 T1-1에서 작성, 정확한 문법은 Claude Code 문서로 확인):
   허용 대상 = 검증된 읽기 전용 `codex exec` 명령 한 종류

### 호출 경로 2가지
| 경로 | 누가 실행 | 용도 |
|---|---|---|
| `/codex:review --base main`, `/codex:adversarial-review <관점>` | **사용자**가 입력 (Claude는 슬래시 명령을 스스로 실행하지 않음) | Phase 게이트에서 사람이 최종 검수 요청 |
| 셸에서 `codex exec` 읽기 전용 실행 | **마스터 AI가 자동** | 작업마다 자동 검수 루프 (아래) |
- `/codex:rescue`(작업 위임)는 코드를 수정할 수 있으므로 이 프로젝트에서 사용하지 않는다.

### Codex 호출 방법 (자동 검수)
- 마스터가 셸로 Codex CLI를 비대화형·읽기 전용 샌드박스로 실행한다(예: `codex exec --sandbox read-only "<검수 요청>"`).
- ⚠ 윈도우에서 읽기 전용 샌드박스가 실제로 적용되는지 T0 단계에서 확인(파일 쓰기 시도가 거부되는지 테스트)하고 결과를 `wiki/tools.md`에 기록.
- ⚠ 플래그명은 설치된 버전에서 `codex --help`, `codex exec --help`로 **먼저 확인**하고 확인된 명령을 `wiki/tools.md`에 기록한다. 추측으로 실행하지 않는다.
- Codex 지침은 루트의 `AGENTS.md`(검수 모드 A~D 정의).
- 검수 요청에는 모드와 필요한 입력만 넘긴다(§1-1 표). 요청 프롬프트에 마스터의 의견·결론을 섞지 않는다.

### 1-1. Codex 검수 규칙 (2026-10-23 추가 — "다른 모델의 독립된 시각"을 살리기 위함)
**검수 시점과 입력**
| 시점 | 모드 | Codex에 넘기는 것 | 넘기지 않는 것 |
|---|---|---|---|
| 구현 전 (위험 작업만) | C 설계 검수 | `plan.md`, 관련 REQ | — |
| 구현·QA 후 1단계 | A 독립 코드 검수 | diff 범위, REQ 수용 기준 | `report.md`, 작업 지시서, 마스터 설명 |
| 구현·QA 후 2단계 | B 보고서 대조 | 1단계 결과, `report.md`, `qa-evidence/<ID>/` | — |
| `intent/` 변경 후, 각 Phase 시작 전 | D 문서 검수 | 변경된 `intent/` 문서 | — |
- **위험 작업**(구현 전 설계 검수 대상): 인증·권한, 오디오 타이밍·동기, DB 스키마·마이그레이션, 외부 모델·라이선스 변경, 공개 API 변경, 세션 처리. (오프라인 캐시는 REQ-09 드롭으로 해당 없음, 2026-10-30)
- 1단계와 2단계는 별도 `codex exec` 호출로 한다(1단계가 보고서에 영향받지 않게).

**지적 처리 규칙** (`logs/<날짜>-<작업ID>-codex.md`에 기록)
- **원칙 (의뢰인 결정, 2026-10-23): Codex 지적은 무조건 수용하지 않는다. 수용 여부의 최종 판단은 사용자가 한다.** 마스터의 역할은 지적을 확인·분류하고 추천 의견을 붙이는 것이며, 아래 "자동 수정" 조건에 해당하지 않는 지적을 스스로 수용하거나 기각하지 않는다.
- 마스터는 모든 지적(`C-xxx`)을 직접 확인한다(재현 시도, 코드·문서 대조). 확인 결과는 **재현됨 / 재현 안 됨 / 확인 불가** 중 하나로 적는다.
- **자동 수정 허용 — 아래 3가지를 모두 만족할 때만**:
  1. 실패하는 테스트·재현 명령·로그로 버그임이 증명됨(마스터가 직접 재현)
  2. 해당 작업의 REQ 범위 안의 국소 수정
  3. 설계·인터페이스·`intent/`·의존성·라이선스·보안 정책의 변경을 수반하지 않음
  → 별도 커밋(`fix(C-xxx)`)으로 수정해 사용자가 게이트에서 쉽게 되돌릴 수 있게 한다.
- **그 외 모든 지적은 "판단 대기"**: 설계·구조·범위·보안 정책·라이선스·성능·스타일·권장·전략 의견, 재현 안 됨·확인 불가, Codex와 마스터 의견이 갈리는 것. 마스터는 수정하지 않는다. 마스터의 의견(동의/반대 + 근거)은 **추천일 뿐 결정이 아니다.** 마스터가 반대해도 항목은 판단 대기로 남는다.
- **판단 대기 항목은 Phase 게이트에서 사용자가 결정**한다: 수용(수정 지시) / 거절(Codex 오탐 또는 불필요, 사유 기록) / 보류. 사용자가 거절한 항목은 해당 지적에 대해 해소된 것으로 보고, 재검수에서 Codex가 다시 올리지 않게 거절 사실을 요청에 포함한다.
- **게이트 보고 표(지적 전체)**: ID / Codex 지적 / 근거 / 마스터 확인 결과 / 마스터 추천 / 상태(자동 수정됨+커밋 ID · 판단 대기) / 사용자 결정 칸. 자동 수정한 항목도 모두 포함한다. 마스터가 지적을 조용히 누락하면 안 된다.
- **즉시 중단 예외**: 데이터 유실·인증 우회·개인 음원 유출 가능성을 지적한 항목은 게이트까지 기다리지 않고 바로 사용자에게 알리고 해당 작업을 멈춘다.
- 판단 대기가 남은 작업은 `main`에 병합하지 않고 작업 브랜치에 둔다. 같은 Phase의 독립 작업은 계속 진행하고, 의존하는 작업은 그 브랜치 위에서 이어가되 `main` 병합은 게이트 결정 이후에 한다.
- 재검수(자동 수정분)는 최대 3회. 3회 뒤에도 REQUEST_CHANGES면 사용자에게 보고하고 멈춘다.

**Codex를 쓸 수 없을 때** (사용량 한도, 로그인 만료, 오류)
- Claude 서브에이전트가 대신 검수하지 않는다("다른 모델" 원칙 보호). 해당 작업을 `Codex 미검수`로 표시하고 사용자에게 보고한다.
- Codex APPROVE 없이는 `main`에 병합하지 않는다. 사용자가 명시적으로 면제한 경우만 예외이며, 면제 사실을 `logs/`에 기록한다.

**효과 측정**
- 각 Phase 게이트 보고에 표를 넣는다: Codex 지적 수 / 수정함 / 반박 / 보류 / 마스터가 사후 판단한 유효 지적 수 / 대략의 사용량 부담. 지적이 거의 유효하지 않다면 검수 빈도·방식을 사용자와 재논의한다.

## 2. 4단계 파이프라인
### ① 기획
- 사용자와 대화로 요구사항 확정 → `intent/`에 명세·투두 반영(사용자 승인 필요).
- 대화 요지는 `logs/YYYY-MM-DD-planning.md`에 기록.

### ② 개발
- 작업 시작 전 `work/<작업ID>/plan.md`: 목표, 근거 REQ, 바꿀 파일, 테스트 계획.
- 구현 후 `work/<작업ID>/report.md`에 **구현 근거** 필수:
  - 각 변경 → REQ ID
  - 사용한 외부 API/라이브러리 → 공식 문서 URL 또는 설치 버전의 타입 정의 위치
  - 확인 못 한 가정 → "가정:" 으로 명시
- 테스트 먼저 작성(가능한 범위에서 TDD).

### ③ QA (증거 기반)
- QA 담당이 직접 실행: 단위 테스트, Playwright E2E, 성능 측정(fps, 오디오 동기 ms, 처리 시간).
- `qa-evidence/<작업ID>/`에 저장: `result.md`(통과/실패 표), 테스트 로그, 스크린샷(PC·폰 뷰포트), 측정값.
- 실패 시: 작업 브랜치를 마지막 통과 커밋으로 되돌리고(롤백) 원인 기록 → 개발 재배정. **최대 3회** 반복 후에도 실패하면 사용자에게 보고하고 멈춤.
- Codex 검수 APPROVE 전까지 반복.

### ④ 위키
- 완료 시 `wiki/`에 갱신: `architecture.md`(구조 변화), `decisions.md`(결정·근거·날짜), `modules/<모듈>.md`, `tools.md`(검증된 명령어).
- 다음 작업은 wiki 요약부터 읽는다.

## 3. 업무 처리 절차 (오케스트레이션)
1. **지시 수신**: 사용자 → 마스터
2. **1차 토론**: 마스터가 관련 담당자를 소집, 각자 **최소 1개 의견**(접근법, 리스크, 질문)을 `logs/<날짜>-<작업ID>-discussion.md`에 남김. Codex도 리스크 의견 1개.
3. **분배·수행**: 토론 결과로 담당·범위 확정. 독립 작업은 병렬(∥). 결과물은 `work/<작업ID>/`, 각 문서 첫 줄 한 줄 요약.
4. **검수**: 마스터 1차 검수(명세 일치) → Codex 전략·리스크 검토
5. **최종 판단**: 마스터가 승인/반려. Phase 게이트는 사용자 승인.

## 4. 병렬·비용 최적화
- 큰 작업은 독립 하위 작업으로 쪼개 병렬 실행 후 마스터가 통합. 같은 파일을 동시에 수정하는 분할 금지.

### 4-1. 병렬 실행 규칙 (2026-10-23 추가)
**서브에이전트 정의**
- 역할별 에이전트를 `.claude/agents/<역할>.md`로 정의한다(마스터가 Phase 1 시작 시 작성, 사용자 승인). 각 파일에 담을 것: 역할 한 줄, 읽을 문서(CLAUDE.md + 담당 REQ), 수정 가능한 폴더, 사용 가능한 도구, 보고 형식(구현 근거 포함).
- 정의 파일 문법·필드는 Claude Code 공식 문서로 확인한 뒤 작성한다(추측 금지). 정의한 내용은 `wiki/tools.md`에 기록.
- 수정 권한은 폴더 단위로 분리: 프론트 = `app/web`, 서버·오디오 = `app/server`, QA = `qa-evidence`, 위키 = `wiki`. 다른 폴더가 필요하면 마스터에게 요청.

**파일 충돌 방지 (git worktree)**
- 병렬 작업 하나당 **별도 작업 폴더(git worktree)** 와 브랜치를 쓴다: `git worktree add ../worktrees/<작업ID> -b task/<작업ID>-<설명>`. 같은 폴더에서 여러 에이전트가 브랜치를 바꾸지 않는다.
- 병렬로 나누기 전 마스터가 작업별 **수정할 파일 목록**을 `work/<작업ID>/plan.md`에 적고, 목록이 겹치면 병렬 금지(순차 진행).
- 병합은 마스터만 한다. 순서는 의존성 낮은 것부터. 병합 충돌 시 해당 에이전트에게 되돌려 재작업. 병합 후 전체 테스트를 다시 돌려 통과해야 완료.
- 작업 끝난 worktree는 정리(`git worktree remove`). `data/`는 worktree마다 복사하지 않고 공용 경로를 참조(커밋 금지 유지).

**측정 작업은 단독 실행 (⏱)**
- 속도·지연·fps·오디오 동기(ms)·처리 시간을 재는 작업은 다른 작업과 동시에 돌리지 않는다. GPU/CPU를 나눠 쓰면 숫자가 왜곡되어 서버 PC 결정, 허용 오차 확정의 근거가 틀어진다.
- 마스터는 측정 시작 전 다른 에이전트의 진행 상태를 확인하고, 측정 중에는 다른 에이전트가 PC 자원을 쓰는 작업(분리·채보·빌드·테스트)을 시작하지 않도록 대기시킨다.
- 측정 보고에는 "단독 실행 여부"와 측정 시점 PC 상태(다른 프로세스 유무)를 적는다.

**동시 실행 수 제한 — 기본 3개**
- 사용량(토큰·Codex 한도)은 "에이전트 수 × 시간"의 합에 거의 비례하므로, 10개가 10분 일하는 것과 4개가 25분 일하는 것의 총 사용량은 비슷하다. 그래도 동시 수를 제한하는 이유:
  1. 사용량 한도는 일정 시간(예: 5시간) 단위라, 짧은 시간에 몰아 쓰면 중간에 멈춘다.
  2. 에이전트가 늘수록 각자 컨텍스트를 새로 읽는 고정 비용이 에이전트 수만큼 추가된다.
  3. 병합·충돌 해결·검수는 마스터와 Codex에 몰리므로 병목이 되어, 늘려도 속도가 비례해 빨라지지 않는다.
  4. 서버 PC의 GPU·CPU·메모리는 하나다.
- 기본 최대 동시 3개. 작업이 모두 독립적이고 PC 자원을 거의 쓰지 않는 경우(문서 정리 등)에만 마스터가 근거를 적고 늘릴 수 있다(최대 5개). 늘릴 때는 사용자에게 먼저 알린다.
- 사용량 한도 경고가 나오면 즉시 동시 수를 1로 줄이고 사용자에게 보고한다.
- 서브에이전트 컨텍스트 = CLAUDE.md + 해당 REQ 문단 + 관련 파일 경로. 고정 순서로 넣어 캐시 재사용.
- 진행 중 맥락이 필요한 분기 작업은 포크 세션 사용.
- 단계별 모델 체급은 CLAUDE.md §2.
